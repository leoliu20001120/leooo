## 一、前端技术评审

### 1. H5/小程序架构评估

#### 1.1 对话 UI 技术选型

| 方案 | 适用场景 | 延迟 | 兼容性 | 推荐 |
|------|---------|------|--------|------|
| **SSE (Server-Sent Events)** | 流式输出、单向推送 | 低 | 好（微信内 WebView 支持） | ✅ **首选** |
| WebSocket | 双向实时通信 | 最低 | 中（微信小程序需特殊处理） | ❌ 本场景无需双向 |
| HTTP 轮询 | 简单场景 | 高 | 最好 | ❌ 体验差，不适合对话流 |

**建议**：STEP 2 的 7 轮对话采用 **SSE**。理由：
- 对话是单向流式输出（王也回复 → 用户），天然匹配 SSE
- SSE 原生支持断线重连，比 WebSocket 更健壮
- 微信内置浏览器对 SSE 的 polyfill 兼容性良好（`EventSource` API 或 `fetch` + `ReadableStream`）
- 降级方案：如遇 SSE 不兼容的极老机型，回退到短轮询（500ms 间隔）

**实现要点**：
```
前端: EventSource / fetch stream → 逐字渲染（打字机效果）
后端: text/event-stream → 每个 token 一个 event
心跳: 每 15 秒一个 keep-alive event，防止代理超时
```

#### 1.2 报告长图渲染方案

| 方案 | 渲染质量 | 性能 | 兼容性 | 推荐 |
|------|---------|------|--------|------|
| **HTML → html2canvas** | 中等 | 客户端渲染，耗时 1-3s | iOS/Android 差异大 | ⚠️ 有风险 |
| **HTML → Puppeteer 服务端渲染** | 高 | 服务端渲染，需排队 | 一致性最好 | ✅ **推荐** |
| Canvas 原生绘制 | 可控 | 快 | 需大量适配代码 | ❌ 开发成本过高 |

**建议**：**服务端渲染（Puppeteer/Playwright）+ 客户端 html2canvas 降级**

**方案细节**：
1. **主链路**：前端将报告数据发给后端 → 后端用 Puppeteer 渲染 HTML 模板 → 生成 PNG → 返回图片 URL
   - 优势：渲染一致性好，不受客户端差异影响
   - 渲染耗时：~2-3 秒（可预渲染 HTML 模板，只注入数据）
   - 需要独立的渲染服务集群（预估 10-20 台 4C8G 实例）
2. **降级链路**：如果服务端排队超时（>5s），降级到客户端 html2canvas
3. **CDN 缓存**：同一用户同一次体检的报告图片缓存 7 天，避免重复渲染

**🔴 Critical 风险**：html2canvas 在部分 Android WebView 中有**字体渲染不一致 + CSS gradient 丢失**的已知问题。必须以服务端渲染为主链路。

#### 1.3 分享组件实现方案

| 场景 | 技术方案 | 说明 |
|------|---------|------|
| 微信好友/朋友圈 | **微信 JS-SDK `wx.updateAppMessageShareData`** | 需公众号/小程序绑定，分享卡片自定义标题+图片 |
| 保存到相册 | **`<canvas>` → `toBlob()` → 下载** 或微信 `saveImageToPhotosAlbum` | 需引导用户授权相册权限 |
| 小红书/微博 | 保存长图 → 唤起 App 分享（Universal Link / URL Scheme） | 无官方 SDK，依赖图片保存 → 手动粘贴 |
| QQ/QQ 空间 | **QQ JS-SDK** | 参考微信 SDK 模式 |

**关键实现**：
- 批命卡分享：**方图 1:1 或 3:4**，直接 Canvas 绘制（内容简单，客户端即可）
- 体检报告分享：**长图 9:16**，服务端渲染（内容复杂，依赖一致性）
- 裂变追踪：每张分享图/链接带 **唯一 `share_id`**，用于归因分析
- 需预埋 utm 参数：`?from=share&share_id=xxx&sharer_uid=xxx`

#### 1.4 响应式适配策略

```
适配层级:
├── 基础: viewport meta + rem/vw 布局（设计稿 375px 基准）
├── 微信内 WebView: WeixinJSBridge + 安全区域适配（底部 home indicator）
├── iOS Safari: 处理 bounce scroll、100vh 问题
├── Android Chrome: 处理软键盘弹出导致的视口变化
└── 微信小程序: 如走小程序方案，用 rpx 单位
```

**建议采用 H5 方案而非小程序**：
- H5 的分享链路更通畅（一个 URL 走遍所有平台）
- 微信小程序的分享只能在微信生态内，无法覆盖微博/小红书
- 性能差异可通过 SSR + 预加载弥补

#### 1.5 前端性能优化策略

| 优化点 | 方案 | 预期效果 |
|--------|------|---------|
| **首屏加载** | 落地页 SSR + Critical CSS inline + 图片 lazy load | FCP < 1.5s |
| **王也立绘** | WebP 格式 + 渐进式加载（骨架屏 → 模糊 → 清晰） | LCP < 2.5s |
| **对话流畅度** | SSE 流式渲染 + 本地动画队列（打字机效果不依赖网络） | 感知延迟 < 1s |
| **报告渲染** | 服务端预渲染 + 前端骨架屏过渡 + 图片预加载 | 渲染感知 < 3s |
| **JS Bundle** | 路由级 code splitting（落地页/对话页/报告页 3 个 chunk） | 每个 chunk < 100KB gzip |
| **网络** | CDN 加速 + HTTP/2 + Brotli 压缩 | 全国 P95 < 200ms RTT |

## 二、后端技术评审

### 1. 高并发架构评估

#### 1.1 双链路方案评估

**离线预生成链路**：

| 设计点 | PRD 方案 | 我的建议 | 理由 |
|--------|---------|---------|------|
| **存储选型** | 未明确 | **Redis Hash + ElasticSearch 辅助** | Redis Hash：`id_hash → [吐槽1, 吐槽2, 吐槽3]`，O(1) 精确匹配；ES：处理模糊匹配查询 |
| **模糊匹配** | Jaro-Winkler | **ES 的 fuzzy query + 自定义评分** | 百万级数据 Jaro-Winkler 逐条计算不现实（O(n) 复杂度），ES 的 BK-tree 索引效率更高 |
| **预生成规模** | 100 万 ID × 3 条 | 合理，约 300 万条 | 存储约 1.5GB（每条 ~500B），Redis 轻松承载 |
| **命中率预估** | ~80% | **60-70% 更保守** | 用户 ID 个性化程度可能高于预期（二次元用户爱取独特名字） |

**🟡 Major 风险**：Jaro-Winkler 模糊匹配在百万级 ID 库上的**暴力计算不可行**。

**替代方案**：
```
方案 A（推荐）: ElasticSearch fuzzy query
  - 创建 ID 索引，配置 fuzziness: "AUTO"
  - 编辑距离 ≤ 2 的匹配，ES 内置 BK-tree 索引
  - 性能：P99 < 50ms（百万级数据）

方案 B: SimHash + 预计算
  - 对每个预生成 ID 计算 SimHash
  - 查询时计算输入 ID 的 SimHash，比较汉明距离
  - 性能：O(1) 查询，但需要额外的索引构建

方案 C: 前缀树 + n-gram 索引
  - 适合中文 ID 的模糊匹配
  - 自建索引，灵活性最高但开发成本也最高
```

**实时推理链路**：

| 设计点 | 建议方案 |
|--------|---------|
| **限流** | 令牌桶（Token Bucket）：全局 30,000 QPM + 单用户 10 RPM |
| **排队** | Redis 有序集合（ZSET）作为优先队列，VIP 用户（已预约）优先 |
| **降级** | 三级降级：① 排队等待 → ② 返回模糊匹配结果 → ③ 返回兜底随机吐槽 |
| **超时** | 推理超时 10s → 强制中断 → 返回兜底回复 |
| **弹性扩容** | K8s HPA，基于 GPU 利用率 70% 触发扩容，最大 3x |

#### 1.2 QPM 预估评审

PRD 预估：峰值 30,000 QPM（STEP 1）

**我的评估**：

```
假设：
- 活动首日 DAU：50 万（参考瓦手首日近半数用户激活）
- 高峰集中度：40% 请求集中在 2 小时（午休 + 晚间）
- 每个用户 STEP 1 请求数：1-2 次

计算：
- 高峰 2 小时请求量：500,000 × 40% × 1.5 = 300,000
- 高峰 QPM：300,000 / 120 = 2,500 QPM
- 峰值突刺（10 分钟内）：≈ 5,000 - 8,000 QPM

活动高峰期（KOL 推荐后）：
- 如果 KOL 视频爆了，短时间流量可能 5-10x
- 极端峰值：25,000 - 50,000 QPM
```

**结论**：30,000 QPM 的预估是**合理的极端场景**，但日常峰值可能只有 5,000-8,000 QPM。建议：
- 基础容量按 10,000 QPM 设计
- 弹性扩容到 50,000 QPM（留余量）
- **关键：离线预生成的命中率决定了实时推理的压力。如果命中率只有 60%（非 80%），实时推理要承接 12,000 QPM 而非 6,000 QPM。**

#### 1.3 对话状态管理方案

**建议**：**Stateless + Context（而非 Server-side Session）**

```
方案: 无状态 + 客户端 Context 传递
  
客户端维护:
{
  "session_id": "uuid",
  "user_id": "xxx",
  "step": 2,
  "round": 3,
  "conversation_context": {
    "id_result": { ... },           // Agent 1 批命结果
    "rounds": [                      // 前几轮问答
      {"q": 1, "answer": "B", "tags": ["勇敢", "进攻型"]},
      {"q": 2, "answer": "A", "tags": ["力量导向"]},
      ...
    ],
    "accumulated_tags": { ... }      // 累计标签
  }
}

每次请求: 客户端将完整 context 发给后端 → 后端注入 Prompt → 无状态推理
```

**理由**：
1. 无状态设计天然支持水平扩展，不需要 sticky session
2. 7 轮对话的 context 数据量小（< 5KB），传输成本可忽略
3. 避免 Redis 存 session 的额外开销和一致性问题
4. 缺点：客户端可能篡改 context → 后端需做 **HMAC 签名校验**

**补充**：用 Redis 做**幂等性控制**（防重复提交）：`SET session_id:round_n NX EX 30`

#### 1.4 数据存储方案

| 数据类型 | 存储方案 | 保留期 | 说明 |
|---------|---------|--------|------|
| **用户画像（格斗画像 + 人格标签）** | MySQL（主表）+ Redis（热数据缓存） | 永久 | 后续阶段复用（游戏内 AI NPC） |

### 2. 安全层评估

#### 2.1 四层安全防护技术实现

| 层级 | 实现方案 | 延迟影响 | 可用性 |
|------|---------|---------|--------|
| **L1 脏词库** | **Aho-Corasick 多模式匹配** + Trie 树 | < 1ms | 99.99% |
| **L2 混元安全模型** | 异步审核（先返回 → 后审核 → 问题内容追溯下线） | 0ms（对用户） | N/A |
| **L3 兜底回复** | Redis 随机抽取 + 场景分类 | < 5ms | 99.99% |
| **L4 人工巡检** | 管理后台 + WebSocket 实时推送异常对话 | N/A | 人工 |

**🟡 Major 建议**：L2 混元安全模型**不应同步阻塞**用户请求。

**优化方案**：
```
原方案（同步）: 用户请求 → AI 生成 → 安全审核(200-500ms) → 返回用户
                                         ↑ 增加 200-500ms 延迟

建议方案（异步）: 用户请求 → AI 生成 → 立即返回用户
                                    ↓
                              异步安全审核 → 问题内容 → 下线/替换
                                         → 正常内容 → 无操作

批命卡例外: 因为批命卡要生成图片持久化，这一步应同步审核
```

#### 2.2 L1 脏词库更新机制

```
更新策略:
├── 基础词库: 5000+ 条，部署时内嵌（编译到代码）
├── 热更新: Redis 存增量词库，每 5 分钟从 Redis 拉取
├── 运营后台: 支持实时新增/删除敏感词 → 写入 Redis → 广播通知
├── 自动学习: L2 审核发现的新敏感模式 → 人工确认 → 加入 L1
└── 特殊时期: 大型活动/敏感日期前手动更新政治敏感词表
```

#### 2.3 L2 混元安全模型延迟影响

- 混元安全模型 P50 延迟：~100ms，P99：~300ms
- 如果同步调用：对话 P99 从 5s 变成 5.3s（可接受），但批命环节从 1s 变成 1.3s（**可能影响 "5 秒出结果" 的承诺**）
- **建议**：批命环节走同步审核（安全优先），对话环节走异步审核（体验优先）

#### 2.4 L3 兜底回复触发逻辑

```python
def get_response(user_input, context):
    try:
        # 1. L1 输入端拦截
        if l1_check(user_input):
            return random_wangye_deflect()  # "这名字不在三界之内"
        
        # 2. 尝试正常推理
        ai_response = await ai_generate(user_input, context, timeout=10)
        
        # 3. L2 安全审核（批命同步/对话异步）
        if is_step1:  # 批命环节，同步审核
            if not l2_check(ai_response):
                return random_wangye_fallback(context.scene)
        else:  # 对话环节，异步审核
            asyncio.create_task(l2_async_check(ai_response, session_id))
        
        return ai_response
        
    except TimeoutError:
        # 超时兜底
        return random_wangye_fallback(context.scene)
    except Exception:
        # 异常兜底
        return random_wangye_fallback("generic")
```

## 三、算法/LLM 评审

### 1. Agent 架构评估

#### 1.1 Workflow 模式 vs 其他方案

| 方案 | 优势 | 劣势 | 适用性 |
|------|------|------|--------|
| **Workflow（3 Agent 串联）** | 可控性强、成本低、调试方便、瓦手验证过 | 灵活性差、无法动态决策 | ✅ **最适合本场景** |
| Agentic（自主决策） | 灵活、可处理意外情况 | 成本高 3-5x、不可控、安全风险大 | ❌ 营销活动不允许不可控 |
| 单 Agent 全搞定 | 最简单 | Prompt 过长、上下文混乱、输出不稳定 | ❌ 15K token Prompt + 7 轮对话会爆上下文 |
| 2 Agent（合并批命+问诊） | 减少一次调用 | 批命和问诊的角色定位不同，合并会降低质量 | ❌ 批命需要快速犀利，问诊需要耐心追问 |

**结论**：Workflow 模式是正确选择。3 个 Agent 职责清晰，每个 Agent 的 Prompt 可以专注优化。

#### 1.2 Agent 间数据传递格式和校验

**建议的数据契约**：

```json

{
  "version": "1.0",
  "agent": "fortune_teller",
  "output": {
    "roast": "string (≤80 chars)",
    "abnormal_star": "int (1-5)",
    "combat_star": "int (1-5)",
    "tone": "enum: [嘴损但认可, 调侃, 冷淡, 惊讶, 欣赏]"
  },
  "metadata": {
    "model_version": "turboS_v2",
    "latency_ms": 1200,
    "from_cache": false
  }
}
```

**校验策略**：
1. **JSON Schema 强校验**：每个 Agent 的输出必须通过 JSON Schema 验证
2. **字段范围校验**：star ∈ [1,5]，roast.length ≤ 80，style ∈ 预定义枚举
3. **降级逻辑**：校验失败 → 重试一次 → 仍失败 → 使用默认值 + 告警
4. **日志追踪**：每个 Agent 的输入/输出全量记录（脱敏后），用于 Prompt 迭代

#### 1.3 Prompt 长度 vs 上下文窗口

```
混元 TurboS 上下文窗口: 32K tokens（预估）

Prompt 预算分配:
├── System Prompt (固定): ~15K tokens
│   ├── 角色设定: ~2K
│   ├── 知识库精选: ~10K
│   ├── 安全规则: ~1K
│   └── 输出格式: ~2K
│
├── Agent 1 (批命):
│   ├── System: 15K (K-V Cache)
│   ├── User Input: ~0.1K (一个 ID)
│   └── 余量: ~17K ✅ 充裕
│
├── Agent 2 (问诊, 第 7 轮):
│   ├── System: 15K (K-V Cache)
│   ├── Agent 1 输出: ~0.3K
│   ├── 6 轮历史对话: ~3K (每轮 ~0.5K)
│   ├── 当前轮输入: ~0.2K
│   └── 余量: ~13K ✅ 充裕
│
├── Agent 3 (出报告):
│   ├── System: 15K (K-V Cache)
│   ├── Agent 1 输出: ~0.3K
│   ├── Agent 2 全量输出: ~4K (性格向量 + 7轮对话)
│   └── 余量: ~12K ✅ 充裕
```

**结论**：32K 窗口下，15K System Prompt + 动态内容完全够用。**但需要严格控制知识库注入的 token 数量**，建议设置硬上限：System Prompt ≤ 16K tokens。

#### 1.4 K-V Cache 策略评估

**可行性**：✅ **高度可行，是本方案的核心性能优化**

```
原理:
  固定 System Prompt (15K tokens) 的 K-V Cache 在模型推理时缓存
  → 每个新请求只需计算用户输入部分的 attention
  → 吞吐量提升 20-30x（瓦手实测从 100 QPM → 3000+ QPM）

实现要求:
  1. 所有 Agent 共享同一个 System Prompt 前缀（至少角色设定 + 知识库部分）
  2. 不同 Agent 的差异化指令放在 System Prompt 尾部或 User Prompt 开头
  3. Cache 需要按 Agent 类型分 3 个池（批命/问诊/出报告）

预估效果:
  - 单实例: 100 QPM → 3000 QPM
  - 10 实例: → 30,000 QPM（满足峰值需求）
  - 成本节省: 推理成本降低 ~70%
```

**🟢 Minor 建议**：K-V Cache 预热——活动上线前 1 小时发送 warm-up 请求，确保 cache 已就绪。

### 2. 模型选择评估

#### 2.1 混元 TurboS 能力评估

| 能力维度 | 要求 | TurboS 表现 | 评估 |
|---------|------|------------|------|
| **角色扮演一致性** | 王也人设不出戏 | 中上（需要强 Prompt 约束） | ⚠️ 需要大量调试 |
| **中文吐槽能力** | 嘴损但有温度 | 良好 | ✅ |
| **JSON 输出稳定性** | 结构化输出 | 良好（配合 function calling） | ✅ |
| **上下文引用** | 回扣前几轮回答 | 中等（7 轮对话可能丢失细节） | ⚠️ 需要显式注入 |
| **推理速度** | 批命 < 5s，对话 < 3s | TTFT ~1s, TPS ~30-50 | ✅ |
| **成本** | 可控 | 低（比 DeepSeek 低 44x） | ✅ |

**结论**：TurboS **基本够用**，但角色扮演的一致性需要 Prompt 工程重点解决。不建议用更大的模型（成本和延迟不划算），也不建议换模型（瓦手的工程基建直接复用 TurboS）。

#### 2.2 Fine-tuning vs 纯 Prompt 工程

| 方案 | 优势 | 劣势 | 推荐 |
|------|------|------|------|
| **纯 Prompt 工程** | 快速迭代、低成本、灵活 | 人设一致性依赖 Prompt 质量 | ✅ **第一阶段首选** |
| Fine-tuning | 人设更稳定、Prompt 更短 | 需要标注数据 + 2-4 周训练 + 迭代慢 | ⚠️ 第二阶段考虑 |

**理由**：
1. 瓦手全程使用纯 Prompt 工程，5000 万次对话验证了可行性
2. 我们有 1125+ 条知识库 + 28 种场景模板，Prompt 工程的素材充足
3. Fine-tuning 的周期（2-4 周数据标注 + 1-2 周训练）不匹配 4 周关键路径
4. **建议在第一阶段上线后，用真实对话数据做 Fine-tuning，第二阶段使用**

#### 2.3 模型输出一致性保证

**问题**：同一个 ID 多次生成可能输出完全不同的吐槽（温度参数导致随机性）

**方案**：
```
1. 批命环节:
   - 离线预生成: 每个 ID 固定 3 条吐槽，用户端随机选 1 条 → 完美一致性
   - 实时推理: 设置 temperature=0.3（低随机性）+ seed 固定 → 近似一致

2. 问诊环节:
   - temperature=0.6（适度随机，保持对话自然）
   - 但性格向量的计算用硬规则（基于选项映射），不依赖模型随机性
   - 王也的回应文字可以不同，但标签/评分必须一致

3. 报告生成:
   - temperature=0.4（偏低，保证评语质量）
   - 六维属性值从 Agent 2 的性格向量**确定性映射**，不经过 LLM
   - 只有深度评语和命运预言走 LLM 生成
```

### 3. 知识库工程评估

#### 3.1 1125+ 条 → 15K token Prompt 的可行性

**计算**：
```
1125 条知识库 × 平均每条 50 字 ≈ 56,250 字 ≈ 75K tokens（中文约 1.3 token/字）

压缩到 15K tokens 需要 5:1 压缩比

压缩策略:
├── 1. 分类精选: 1125 条 → 按场景频率排序 → 选出高频 300 条
├── 2. 合并同类: 多条知识压缩为一条概括性规则
│     例: 10 条张灵玉相关 → 1 条 "张灵玉性格：刚正不阿，武当嫡传大弟子，与王也亦师亦友"
├── 3. 分层注入: 核心知识（~10K）固定注入 + 场景知识（~5K）动态注入
│     - 批命 Agent: 注入 "ID 解读 + 道家哲学 + 格斗梗" 相关知识
│     - 问诊 Agent: 注入 "人物关系 + 世界观 + 修行哲学" 相关知识
│     - 出报 Agent: 注入 "角色映射 + 评语模板" 相关知识
└── 4. Few-shot 替代: 部分知识用 2-3 个高质量 example 替代长规则
```

**🟡 Major 建议**：不要试图把 1125 条全塞进 Prompt。应该做**分层知识库**：

```
Layer 1 (核心, 固定注入, ~8K tokens):
  - 王也核心人设 (性格、语气、口头禅)
  - 关键人物关系 (5-10 人)
  - 核心世界观 (甲申之乱、门派体系)

Layer 2 (场景, 动态注入, ~5K tokens):
  - 根据 Agent 类型注入不同子集
  - 根据对话上下文动态选取相关知识

Layer 3 (长尾, 不注入 Prompt):
  - 存在检索系统中
  - 只在用户提到特定关键词时通过 RAG 检索注入
  → 但本阶段是结构化体检，不是开放聊天，可能用不到 RAG
```

**结论**：15K token 的 Prompt 可行，但需要精心设计分层注入策略。**建议 Prompt 工程阶段的第 1 天专门做知识库筛选和压缩**。

#### 3.2 格斗知识库（130 条新增）优先级

| 优先级 | 模块 | 条数 | 理由 |
|--------|------|------|------|
| **P0** | 格斗术语映射（50 条） | 50 | 直接影响报告质量（"连招"→"绵绵若存"）|
| **P0** | 格斗哲学（30 条） | 30 | 王也作为格斗高手的核心知识 |
| **P1** | 角色格斗风格（30 条） | 30 | 12 种风格映射需要，但可从现有知识推导 |
| **P2** | 擂台场景回复（20 条） | 20 | 本阶段是结构化问答，开放场景回复优先级低 |

**建议**：P0 的 80 条优先建设（2 天），P1 在联调阶段补充，P2 可推迟。

#### 3.3 Prompt 结构优化建议

```markdown
# System Prompt 优化结构（建议）

## [角色定义] ~1K tokens
你是王也...（精简核心人设）

## [知识库 - 核心] ~4K tokens  
### 核心人物关系（5-10 人精选）
### 核心世界观（甲申之乱简述）
### 王也格斗哲学（后发先至、风后奇门）

## [知识库 - 格斗] ~3K tokens（新增）
### 格斗术语 → 道家翻译（表格，50 条精选 → 20 条高频）
### 12 种格斗风格定义（简表）

## [任务指令] ~3K tokens
### 当前 Agent 的具体任务
### 输入/输出格式
### Few-shot 示例（2-3 个）

## [安全规则] ~1K tokens
### 红线（绝不输出的内容）
### 边界约束

## [输出格式] ~1K tokens
### JSON Schema
### 字数限制
```

**关键优化点**：
1. **知识库用表格而非叙述**——表格更紧凑，节省 30-40% token
2. **Few-shot 示例必须覆盖边界情况**——正常 ID、敏感 ID、空白 ID
3. **安全规则放在尾部**——LLM 对 Prompt 尾部的 attention 更高

### 关键路径分析

**PRD 声称关键路径 4 周，我认为是 5 周。原因**：

1. **Prompt 工程不能完全并行**：Agent 2 依赖 Agent 1 的输出格式，Agent 3 依赖 1+2。串行至少 2.5 周
2. **联调被低估**：3 个 Agent 串联 + 前后端对接 + 安全层 + 压测，4 天不够，至少 7 天
3. **内测迭代需要时间**：IP 粉内测反馈 "不像王也" 后需要改 Prompt → 重新测试 → 再内测，一轮至少 3 天

**建议**：
- 关键路径 **5 周**
- 总周期 **6-7 周**（含 1-2 周缓冲）
- 如果必须 4 周上线，需要：① 砍掉 IP 粉内测（高风险）② 压缩联调到 3 天（高风险）③ 增加人力（前端 3 人、后端 2 人）

## 附录：技术决策备忘

| 决策项 | 推荐方案 | 备选方案 | 决策理由 |
|--------|---------|---------|---------|
| 对话推送 | SSE | WebSocket / 轮询 | 单向流式、断线重连、兼容性好 |
| 报告渲染 | Puppeteer 服务端 + html2canvas 降级 | 纯客户端渲染 | 一致性 > 性能（营销物料质量是核心） |
| 模糊匹配 | ElasticSearch fuzzy | Jaro-Winkler 暴力 | 百万级数据性能不可行 |
| 状态管理 | Stateless + HMAC 签名 | Server-side Session | 水平扩展 + 无状态设计 |
| 安全审核 | 批命同步 + 对话异步 | 全同步 | 平衡安全和体验 |
| LLM | 混元 TurboS + 纯 Prompt | Fine-tuning | 时间、成本、灵活性优先 |
| 前端载体 | H5（非小程序） | 微信小程序 | 跨平台分享 > 微信内体验 |

## 六、跨团队联动议题（产品 + 测试反馈回应）

> 以下内容基于产品经理和测试负责人的反馈补充。

### 6.1 不完整报告功能（产品反馈 #1）

**需求**：用户完成 ≥4 轮问答后退出，应自动生成简化版报告。

**技术可行性**：✅ 可行，但需要增加 1-2 天工作量。

**实现方案**：
```
Agent 3（出报 Agent）改造:

输入分两种模式:
├── 完整模式: 7 轮对话全部完成 → 输出完整报告 (现有逻辑)
└── 简化模式: 4-6 轮对话 → 输出简化报告 (新增)

简化报告差异:
├── 格斗画像: 已回答维度正常计算，未回答维度用"待解锁"代替数值
├── 异人人格: 门派/师父基于已有数据推断，标注"初步判定"
├── 深度评语: 缩短为 1-2 句 + "可惜你没聊完，不然我能说得更准"
└── 命运预言: 固定兜底："未完之局，等你回来续上"

触发逻辑:
├── 前端: 用户关闭/后退 → 弹窗"要不要先出个简版报告？" 
│         → 确认 → 发送已有 context 到后端
├── 后端: 检查 rounds_completed ≥ 4 → 调用 Agent 3 简化模式
└── 超时: 用户 5 分钟无操作 → 自动生成 → 推送通知
```

**Agent 3 Prompt 改造**：在 System Prompt 中增加条件分支：
```
[条件] 如果对话轮数 < 7:
  - 明确告诉用户"体检未完成"
  - 已有维度正常分析，缺失维度标注"?"
  - 评语风格: 欲言又止 + 引导回来完成
  - 例: "聊了四轮就跑？行吧，先给你出个半成品。想看完整版的，回来找我。"
```

**工作量影响**：Agent 3 Prompt +1 天，前端弹窗逻辑 +0.5 天，后端路由 +0.5 天。

### 6.2 全局降级策略（产品反馈 #2）

**问题**：PRD 只有 AI 输出层面的降级，缺少整体服务不可用时的方案。

**全局降级分级**：

| 降级等级 | 触发条件 | 降级措施 | 用户感知 |
|---------|---------|---------|---------|
| **L0 正常** | 一切正常 | 无 | 正常体验 |
| **L1 轻度** | AI 推理延迟 P99 > 8s | 批命走离线库 only（停止实时推理） | 批命秒出但可能不够个性化 |
| **L2 中度** | AI 服务部分不可用 / QPM 超限 | STEP 2 降级为纯选项模式（无 AI 追问） | 对话变固定脚本 |
| **L3 重度** | AI 服务完全不可用 | 整站降级为静态版：固定批命 + 固定问卷 + 模板报告 | 体验大幅降级但功能可用 |
| **L4 熔断** | 核心服务崩溃 | 展示"王也闭关中"等候页面 + 预计恢复时间 | 完全不可用 |

**L3 静态降级版本**（需提前准备）：
```
准备工作:
├── 100 条预写的固定批命吐槽（按 ID 类型分类：中文名/英文名/数字/特殊符号）
├── 7 轮固定问卷（无 AI 追问，纯选项，每个选项预写固定回复）
├── 12 种格斗风格的模板报告（每种 3 个变体）
└── 前端: 一个开关控制是否走 AI 或走静态
```

**实现**：前端通过 Feature Flag（配置中心）切换降级等级，运维可实时调整。

### 6.4 H5 vs 小程序（产品反馈 #4）

**明确建议：✅ H5 为主，不做小程序。**

| 维度 | H5 | 小程序 | 结论 |
|------|----|----|------|
| 跨平台分享 | URL 直达所有平台 | 仅微信内 | ✅ H5 胜 |
| 开发成本 | 一套代码 | 需额外适配 | ✅ H5 胜 |
| 微信内体验 | 中等（WebView） | 优（原生组件） | 小程序略胜 |
| 保存到相册 | 需要引导授权 | 原生 API | 小程序略胜 |
| KOL 分发 | B站/抖音/微博/小红书全覆盖 | 仅微信 | ✅ H5 胜 |
| 预约转化 | 跳转预约页（URL） | 跳转小程序/H5 | 持平 |

**如果后续需要小程序**：用 WebView 嵌入 H5 页面即可，不需要原生重写。

### 6.5 K-V Cache 淘汰策略与监控（测试反馈 #1）

**Cache 淘汰策略**：
```
K-V Cache 管理:
├── 缓存对象: 3 个 Agent 的 System Prompt K-V 向量
├── 生命周期: LRU（最近最少使用），保持热度
├── 容量: 每个 Agent Pool 维持 10 个缓存副本
├── 淘汰条件: 
│   ├── System Prompt 更新 → 全量失效 → 重新预热
│   ├── 实例重启 → 该实例 cache 丢失 → 自动重建
│   └── 30 分钟无请求的 cache 自动淘汰
├── 预热: 活动上线前 1 小时，每个 Agent 发送 100 次 warm-up 请求
└── 监控:
    ├── Cache 命中率 (目标 ≥ 95%)
    ├── Cache Miss 后首次推理延迟
    ├── Cache 重建耗时
    └── 告警: 命中率 < 80% → P1 告警
```

### 6.6 双链路切换阈值配置（测试反馈 #2）

**确认：阈值参数可配置。**

```yaml
# 双链路配置 (配置中心, 可热更新)
routing:
  # 精确匹配 (Redis Hash)
  exact_match:
    enabled: true
    timeout_ms: 100
  
  # 模糊匹配 (ElasticSearch fuzzy)
  fuzzy_match:
    enabled: true
    timeout_ms: 500
    min_score: 0.75          # ← 可调节: 匹配分数阈值 (0-1)
    fuzziness: "AUTO"        # ← 可调节: 编辑距离策略
    max_expansions: 50       # ← 可调节: 最大扩展数
  
  # 实时推理 (混元 TurboS)
  realtime:
    enabled: true
    timeout_ms: 10000
    max_qpm: 30000           # ← 可调节: 限流阈值
    queue_max_size: 5000     # ← 可调节: 排队上限
  
  # 降级策略
  fallback:
    order: ["exact", "fuzzy", "realtime", "fallback_pool"]
    fallback_pool_size: 200  # 兜底回复池大小
```

### 6.7 对话中途退出状态策略（测试反馈 #3）

**建议：不恢复，而是提供"简版报告 or 重来"的选择。**

```
用户中途退出 STEP 2 后再次进入:

方案 A (恢复): 服务端存 session → 用户回来继续 → 复杂度高
方案 B (推荐): 无状态 + 前端 localStorage → 用户回来选择:
  ├── "继续上次体检" → 从 localStorage 恢复 context → 继续
  ├── "重新开始" → 清空 context → 从头来
  └── "出简版报告" → 发送已有 context → Agent 3 简化模式

实现:
  - 前端: 每轮对话后将 context 写入 localStorage (key: session_id)
  - 过期: localStorage 数据 24 小时后自动清理
  - 安全: context 带 HMAC 签名，防篡改
```

### 6.8 排队机制 UX（测试反馈 #5）

**排队触发/恢复逻辑**：
```
触发: 实时推理 QPM > 30,000 (令牌桶耗尽)
  → 新请求进入 Redis ZSET 优先队列 (score = timestamp)
  → 已预约用户 score -= 10000 (优先处理)

前端 UX:
  ┌──────────────────────────────┐
  │                              │
  │  王也正在看别人的面相，       │
  │  前面还有 {N} 人...          │
  │  预计等待 {T} 秒              │
  │                              │
  │  [道家修行讲究"等"]           │
  │  ───────────────────         │
  │  💡 小知识: {随机王也知识}     │
  │                              │
  └──────────────────────────────┘

恢复: 
  QPM < 25,000 (留 17% 余量) → 停止排队，直接处理
  排队超过 60 秒 → 降级到兜底回复 + "王也今天看太多人了"
```
