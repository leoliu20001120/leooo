# 原型先行交付法

> 💡 核心洞察：AI 时代，产品经理的默认交付物应该从 PRD 转向可交互原型。
> 📅 沉淀日期：2026-03-25

---

## 背景

传统产品流程中，PRD 是产品经理的核心交付物。但 PRD 本质上是用「低带宽媒介」（文字）传递「高带宽信息」（交互体验），每次转译都有信息损耗：

```
产品经理脑中的画面 → 文字描述 → 开发者脑中的画面
```

AI 工具（如 CodeBuddy、Cursor 等）将原型制作成本降到接近零，使得「原型先行」成为可能且合理的默认选择。

## 核心观点

### 1. 原型是更好的思考工具

> 💎 **文字只能传递逻辑，原型才能传递体感。**

- 文字写需求时，很多体验问题**想不到**
- 看到实际界面时，问题会**自己跳出来**
- 用「做」来想，比用「写」来想更快发现问题
- **前置排雷**：产品经理在原型阶段就能体验到实际效果，提前发现并解决问题，而不是等开发完成后才踩雷
- 人对交互体验的判断靠「体感」而非「逻辑」——文字是逻辑通道，原型是体感通道

### 2. PRD 角色重新定位

PRD 不会消失，但从「施工图纸」退化为「决策备忘录」：

| PRD 保留的 | 原型承担的 |
|-----------|-----------|
| **Why** — 为什么做（背景、目标、指标） | **What** — 做成什么样（界面、交互、流程） |
| **决策记录** — 为什么选方案 A 不选 B | **体验验证** — 方案 A 实际用起来如何 |
| **边界条件** — 异常情况怎么处理 | **主流程演示** — 正常路径长什么样 |

### 3. 产品经理能力迁移

```
以前：需求分析 → 写文档 → 画原型 → 跟进开发
现在：需求分析 → 直接出原型 → 体验验证 → 快速迭代 → 附决策文档
```

- ⬇️ 下降：文档撰写能力
- ⬆️ 上升：问题定义能力、快速验证能力、AI 工具驾驭能力

## 适用场景

- ✅ 新功能设计（尤其是交互密集型）
- ✅ 向项目组/开发同步需求
- ✅ 方案评审和对齐
- ✅ 产品经理自己验证想法

## 注意事项

- ⚠️ 警惕「界面驱动思维」陷阱 — 先想长什么样，再想解决什么问题是本末倒置
- ⚠️ 原型无法替代 Why 的思考 — 背景、目标、指标仍需文字沉淀
- ⚠️ 边界条件仍需文字补充 — 异常流、权限、兼容性等原型难以全面覆盖

## 一句话总结

> **PRD 从"施工图纸"变成了"决策备忘录"，原型从"锦上添花"变成了"默认交付物"。产品经理用原型前置排雷，用 PRD 记录决策。**
