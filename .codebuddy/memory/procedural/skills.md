## 已验证工作流

### 📖 读书笔记 → 课程化
**触发**: 用户说"课程化"或"同样处理"

1. 读取现有笔记 → 了解已有内容和结构
2. Web搜索原书目录 + 中文读书笔记（知乎/GameRes等）
3. 按原书章节拆分，每章一个 md 文件
4. 创建TODO → 按批次（4-5章一组）
5. 批量创建: `_README.md` + 各章 + `附录_速查表.md`
6. 每章格式: 核心内容 → 案例 → 练习 → 金句 → 延伸阅读 → 章节导航 → 跨书关联
7. 写入 episodic 日志

**已应用**: 《游戏设计艺术》36文件、《快乐之道》16文件

### 📊 知识库扩充
**触发**: 用户要求扩充/补充知识库

1. 读取现有知识库 → 了解范围和格式
2. Web搜索+爬取 → 多来源获取新数据
3. **交叉校验** → 与现有数据比对，标注冲突/新增
4. 结构化整理 → Excel多Sheet分类
5. **独立文件存储** → 绝不覆盖已有文件
6. 输出校验报告

### 🎨 产品原型迭代

1. **第一性原理Review** → 从用户任务出发审视
2. 问题分类 → 按严重度排序（🔴🟡🟠）
3. 设计改进 → 不追求视觉炫技
4. 实现 + 更新说明文档 + 版本号递增

### 🌐 H5 Demo 快速原型
**触发**: 用户要求做 H5 Demo / 营销页 / 交互原型

1. PRD + Mock 数据契约 → 定义接口和数据结构
2. 单文件 HTML（CSS+JS 内联）→ 快速出 MVP
3. Mock 数据逻辑 → 纯前端模拟（哈希/随机/状态机）
4. 视觉升级 → 逐步 replace_in_file（避免 token 溢出），不要一次性重写
5. 内容升级 → 替换文案/题目/对话，保持结构不变
6. 功能迭代 → 新增组件（Bottom Sheet / 粒子系统等）

**已应用**: 异人体检站 H5 Demo（5轮迭代）

### 🤖 AI 团队多角色评审
**触发**: 用户要求做评审 / 技术方案评估 / 综合评估

1. 组建多角色团队（常用: PM / Tech-Lead / QA-Lead / Project-Manager）
2. 各角色独立产出评审文档
3. 跨团队意见交叉验证 → 达成共识
4. main 角色汇总 → 综合评审报告
5. 后续交付物：开发启动包（Kickoff材料 / TAPD任务 / Week1清单 / 埋点）

**已应用**: 异人体检站 PRD 评审（4角色，产出9份文档）

### 🎮 UC 对局复盘测试闭环
**触发**: 用户说"ucgit pull/push/commit"或涉及 analysis.go 修改

1. `git pull` 拉最新代码
2. 修改 `analysis.go`
3. `git add + commit + push`（master 分支 → git.woa.com）
4. 运行 `upload_and_report.py` 批量测试 46 个 JSON
5. 分析 `result.xlsx` → 对比变化 → 数据可视化

### 📝 需求文档分级审查
**触发**: 撰写/生成任何需求文档、方案文档、评估报告时

1. **写前三问**（强制）
   - 给谁看？→ 看了做什么决策？→ 成功交付标准？
   - 答不清楚 = 不动笔
2. **定级**
   | 级别 | 判断标准 | 策略 |
   |------|----------|------|
   | 🟢 轻量 | 内部沟通、无决策 | 写后自查（结构+完整性） |
   | 🟡 中等 | 影响团队决策 | 写后切对立角色审一遍 |
   | 🔴 重型 | 影响立项/上线/跨团队 | [[AI团队多角色评审法]] 完整流程 |
3. **默认中等**——不确定时按中等走
4. **只升不降**——审查中发现问题多，自动升级

**已应用**: product-manager Rule 已植入完整分级审查段落

### 🔄 Self-Improvement 持续改进
**触发**: 以下任一场景发生时，**必须**调用 `self-improvement` Skill

| 触发场景 | 动作 |
|---------|------|
| 工具/命令执行失败 | 记录失败模式 + 根因 + 修复方案 |
| 用户纠正我的方案（"不对"/"其实应该…"） | 立即触发，记录纠偏前后对比 |
| 发现比当前更优的方法 | 记录 before/after + 为什么更好 |
| 外部 API/工具不可用或行为异常 | 记录降级策略 |
| 会话结束前 | 回顾本次是否有值得沉淀的改进点 |
| **同类错误累计 ≥3 次** | **触发规则提炼（见下方自动化流程）** |

**与记忆系统的分工**：
- 记忆系统（episodic/procedural）= **记住做了什么、踩了什么坑**
- self-improvement Skill = **系统化地分析为什么出错、怎么变更好**
- 两者互补：self-improvement 产出的洞察 → 沉淀到 procedural/skills.md 错题本

**反模式**：
- ❌ "先把活干完再说" → 改进点会被遗忘
- ❌ 只在 episodic 记一笔就了事 → 没有系统化分析
- ✅ 触发时立即调用 Skill，哪怕只花 30 秒

### 🔁 错误→规则自动化（Harness 自进化）
**触发**: 每次向错题本写入新条目时

**流程**：

```
错误发生
  ↓
① 记录到错题本（日期 + 坑 + 教训）     ← 现有流程
  ↓
② 归类打标签（类别: 系统运维/产品设计/数据处理/代码迭代/文档质量/...）
  ↓
③ 检查同类累计数量
  ↓
  ├─ < 3 次 → 正常流转，结束
  ↓
  └─ ≥ 3 次 → 🚨 触发规则提炼
        ↓
      ④ 分析 3+ 次错误的共性根因
        ↓
      ⑤ 提炼为一条硬性规则，格式：
         "在 [场景] 下，必须 [动作]，否则 [后果]"
        ↓
      ⑥ 写入对应 Rule 文件 / SOP 步骤
         - 数据相关 → data-analyst Rule
         - 产品相关 → product-manager Rule
         - 代码相关 → skills.md 测试闭环工作流
         - 系统相关 → procedural/tools.md
        ↓
      ⑦ 在错题本中标注"已提炼为规则"
         格式: 教训列追加 "→ ✅ 已提炼为规则 [规则摘要]"
        ↓
      ⑧ episodic 日志记录提炼事件
```

**分类标签（用于归类统计）**：

| 标签 | 适用场景 | 规则落地位置 |
|------|----------|-------------|
| `运维` | macOS配置、脚本、定时任务 | procedural/tools.md |
| `设计` | UI/UX、产品设计决策 | product-manager Rule |
| `数据` | 口径、数据处理、分析方法 | data-analyst Rule |
| `代码` | 逻辑错误、测试遗漏 | skills.md 测试闭环 |
| `文档` | 格式、遗漏、质量 | product-manager Rule |
| `工具` | 工具配置、兼容性 | procedural/tools.md |

**关键约束**：
- 提炼的规则必须是**可执行的强制动作**，不是"注意XXX"这种软提醒
- 规则格式统一："在 [场景] 下，必须 [动作]"
- 每次提炼后**立即验证**：这条规则能否阻止之前的 3 次错误？不能则重写
- 提炼后的错题本条目不删除，保留历史（但标注已提炼）

## 思维与输出原则

### 🧱 第一性原理
- 每个决策/分析前，**回到最基本的事实和约束**，追问"为什么"直到触底
- 不接受"因为大家都这么做"作为理由，从底层逻辑推导

### 🔍 批判性思维
- 对假设保持怀疑：我的前提成立吗？有没有反例？
- 区分**事实 vs 观点 vs 推测**，明确标注不确定性
- 主动寻找反面论据，不做选择性呈现

### 🔺 金字塔原理（输出结构）
- **结论先行**：开头直给答案/核心观点
- **分组归类**：同类信息归到一起，MECE（互斥穷尽）
- **逻辑递进**：每组内部按逻辑顺序排列（时间/重要性/因果）
- 所有文档输出必须结构化，拒绝"意识流"式铺陈

### 📅 每周方法论沉淀（周五自动）
**触发**: 每周五会话时主动执行（无需用户指令）

1. 读取最近 7 天 `episodic/` 日志
2. 识别有沉淀价值的工作模式、分析方法、流程创新
3. 对比 `30_Common/方法论/` 已有内容，避免重复
4. 新方法论 → 创建 .md 到 `30_Common/方法论/`
5. 已有方法论需补充 → 更新对应文件（追加实战案例/改进）
6. 更新 `30_Common/_README.md` 索引
7. 在当天 episodic 日志记录沉淀结果

**判断标准**: 只沉淀跨项目可复用的方法，不记录项目特定细节。本周无新增则记录"本周无新增方法论"。
