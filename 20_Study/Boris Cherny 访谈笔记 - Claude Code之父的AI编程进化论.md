## 二、Claude Code 的诞生与演进

### 2.1 从 AppleScript 到产品

```
阶段 1：CLI 聊天工具
├── 起初只是为了熟悉 Claude 3.6 API 写的终端聊天工具
├── 连接 AppleScript，用来查询/更改工作时听的音乐
└── 是个很酷的 Demo，但没引起太大轰动

阶段 2：接入 Tool Use → 顿悟时刻
├── 当模型接入工具后，它自己写出脚本来查询当前播放的音乐
├── 💡 顿悟："模型就是一个主体，应该让它自己用工具去完成事情"
└── 不是把模型框死在系统里，而是给它"手脚"

阶段 3：代码库探索 → Product Overhang
├── 与 PM Cat Wu 交谈后，让终端能读写文件、运行命令
├── Claude 开始自主探索文件系统（读取文件 → 查看引用 → 继续读取）
└── Boris 将此称为"产品过载"——模型已有能力，但无产品释放它

阶段 4：内部病毒式传播
├── 2024.11 内测版发布
├── 第 1 天：20% 工程团队在用
├── 第 5 天：50% 工程团队在用
└── 内部争论是否"当秘密武器" → 最终决定发布

阶段 5：公开发布 → 10 亿美元 ARR
├── 2025.5 GA（Generally Available）
├── 上线 6 个月创造近 10 亿美元年化营收
└── 全球公开提交的代码中约 4% 由 Claude Code 编写
```

### 2.2 技术栈选择

| 组件 | 技术 | 选择原因 |
|------|------|----------|
| **主语言** | TypeScript | "在分布上"——模型已非常熟悉，无需额外学习 |
| **UI** | React with Ink | 在命令行中渲染交互式组件 |
| **布局** | Yoga（Meta 开源） | 处理不同终端尺寸的约束布局 |
| **构建** | Bun | 比 Webpack/Vite 更快 |
| **分发** | npm | 全球开发者最熟悉的生态 |

### 2.3 架构哲学："少即是多"

- **极简壳层**：Claude Code 本质是模型之上的轻量级壳层
  - 定义 UI → 暴露 Hooks → 提供工具 → 然后"让路"
- **不用 RAG**：放弃复杂的向量数据库，直接让模型用 `grep` 和 `glob` 搜索代码
  - 💡 给模型强大的工具 > 给它复杂的索引数据库
- **无虚拟化**：本地运行，直接执行 bash，不用 Docker/云沙盒
- **删代码文化**：每当新模型发布（如 4.0），就删除大量代码（甚至删掉一半系统提示词）
- **权限系统**：最复杂的部分——多层级配置（项目/用户/公司），操作前请求批准
- **安全**：采用"瑞士奶酪模型"分层防御（模型对齐、运行时分类器、子进程摘要）

## 三、⭐ 核心亮点：一天半做 20 个原型

> 🔑 **这就是你说的"一天半做原型"的具体出处**

### 3.1 背景
Anthropic 的工程文化**拒绝写 PRD**（产品需求文档），推崇"**Show, don't write**"——直接做原型、演示验证，而非写文档对齐。

### 3.2 具体案例：待办事项列表功能

Boris 在 Pragmatic Engineer 文章中详细记录了开发"待办事项列表"功能的过程：

**效率对比**：
- 🐢 **传统开发**：两天时间，通常只能做 2 个原型
- 🚀 **AI 辅助开发**：两天内制作了约 **20 个实际可运行的原型**

**迭代过程速记**：
```
原型 #1  → 待办列表固定在输入框上方
原型 #2  → 改为内联显示，只在处理时显示标题
原型 #3-4 → 尝试"交互式药丸"，类似后台任务
原型 #5-6 → 改成"抽屉"模式，右侧滑入 + 动画
原型 #7-9 → 回到输入框上方，调截断和标题样式
原型 #10-20 → 持续调可见性和位置
最终版  → 放在加载 Spinner 中 + CTRL+T 切换显示
```

## 四、Boris 的极致工作流

### 4.1 "代码指挥官"模式
- 每天提交 **20-30 个 PR**
- **100% 的代码由 AI 生成**（自 Opus 4.5 开始已卸载 IDE）
- 自称已从"代码手艺人"转型为"代码审查员 + 任务编排者"

### 4.2 并行工作流
```
本地端：同时开 5 个 Claude Code 终端
├── Tab 编号 1-5
├── 通过系统通知知道哪个 Claude 需要输入
└── 每个跑不同的独立任务

云端：同时跑 5-10 个 claude.ai/code
├── 本地和云端之间可"传送"会话
└── 用 & 把本地会话推到云端继续跑
```

### 4.3 模型选择
- **只用 Opus 4.5 with thinking**
- 虽然比 Sonnet 大、慢，但：
  - 不用怎么纠正它
  - 工具使用更好
  - **最终反而更快**

### 4.4 CLAUDE.md 实践
- 团队共享一份 `CLAUDE.md`，提交到 Git，每周有人贡献更新
- 原则：不是"写说明书"，而是"写**最小纠偏规则**"
  - 发现模型犯错 → 总结成规则写进去
  - ⚠️ 如果文件过长，**删掉重来**（模型每代能力都在变，旧规则可能失效）

## 五、Anthropic 独特的工程文化

### 5.1 扁平化职称
- 全员职称均为 **"Member of Technical Staff"（MTS）**
- 目的：承认大家都在摸索、鼓励通才模式、打破角色边界
  - 工程师也做产品，设计师也写代码

### 5.2 不写 PRD
- 几乎不写产品需求文档
- 推崇"直接做原型、演示验证"
- 💡 核心理念：构建成本已降低到可忽略不计，正确答案需要快速尝试来摸索

### 5.3 发布频率
- **内部发布**：每天 60-100 次
- **外部发布**：几乎每天一个新版本
- **PR 产出**：夏天期间工程师平均每天 5 个 PR（行业通常 1-2 个）

### 5.4 效率数据
- Anthropic 工程团队人数翻倍，同时人均 PR 产出增加 **67%**
  - 通常团队扩容会降低人均产出，Claude Code 扭转了这一趋势
- 人均工程师生产力提升 **150%**
- **90% 的 Claude Code 代码是由 Claude Code 自己编写的**
- 约 80% 的 Anthropic 编写代码的工程师每天都在使用 Claude Code

### 5.5 代码审查新模式
```
Claude Code 自动抓取 ~80% 的 Bug 并自测
         ↓
Claude Code 甚至能编写 lint rule
         ↓
最终由人类工程师进行最终批准 ✅
```

## 六、核心理念与金句

### 6.1 产品哲学
> **"不要为今天的模型做产品，要为六个月后的模型做产品。"**
> — 不要为了解决当前模型缺陷而构建复杂脚手架，下一代模型更新后这些就成技术债

### 6.2 模型本质
> **"模型不是来陪聊的，它是来动手的。"**
> — 聊天只是入口，一旦给它"手脚"（Bash、API、文件控制），它就像能干活的同事

### 6.3 The Bitter Lesson
> **"通用的方法（利用算力）最终一定会战胜专用的方法。"**
> — 不要押注模型做不到。权衡：现在投工程资源换 10-20% 提升 vs 等模型进化免费获得

### 6.4 印刷机隐喻
> **"程序员正处于 15 世纪印刷机发明前'抄写员'的时刻。"**
> — 虽然抄写员消失了，但识字和书写的普及让"作者"的市场扩大了一万倍

### 6.5 工程师角色转变
| 应放弃 | 应坚持 | 新技能 |
|--------|--------|--------|
| 对代码风格、语言、框架的执念 | "假设驱动"思维 | "短注意力"——管理多 agent 并行 |
| 亲自编写每行代码 | 好奇心、开放心态 | 系统定义能力 |
| 深度沉浸式工作模式 | 适应力 | 跨学科"超级通才" |

## 七、多 Agent 协作架构

### 7.1 Agent Topology（智能体拓扑）
- 核心概念："非相关上下文窗口"——让多个 Agent 拥有独立、干净的上下文
- 增加上下文 = 增加"测试 + 计算"，配合合适的拓扑结构能构建更复杂的东西

### 7.2 子 Agent 机制
- 大多数 Agent 是由 Claude 触发的**递归子 Agent**
- 场景示例：修复复杂 Bug 时，启动多个子 Agent
  - Agent A：看日志
  - Agent B：分析代码路径
  - Agent C：做研究
  - 最后汇总结果

### 7.3 Claude Teams
- 允许 Claude 创建多个 Agent，给它们分发任务
- 甚至可以在 Asana 看板上自动创建任务并分配

## 💡 关键启示（个人批注）
