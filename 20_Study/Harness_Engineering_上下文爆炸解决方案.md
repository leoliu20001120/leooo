# Harness Engineering 解决上下文爆炸问题

> 创建: 2026-03-31 | 背景: 任务执行频繁遇到上下文爆炸
> 信息来源: Anthropic 官方博客、LangChain Deep Agents 实验、Claude Code Best Practices 社区共识、Harness Engineering 综合方法论

---

## 📋 结论先行

**上下文爆炸不是模型能力问题，而是工程控制问题。** Harness Engineering 提供了一套系统化的解决框架：

| 策略层 | 核心思路 | 预期效果 |
|--------|---------|---------|
| 🏗️ 上下文架构 | 分层注入，延迟加载 | 减少 50%+ 基线 token 消耗 |
| 🔄 生命周期管理 | 主动清理 + Document & Clear | 避免达到上下文上限 |
| 🤖 子代理委派 | 重型任务拆分到子代理 | 主代理上下文保持精简 |
| 📝 持久化记忆 | 结论→文件，过程→丢弃 | 跨会话连续性，零上下文开销 |
| ⚙️ 工具与 MCP 治理 | 精简工具集，控制输出长度 | 减少单次工具调用的 token 占用 |

---

## 1. 为什么上下文会爆炸？——根因分析

### 1.1 关键研究发现

> **当上下文窗口利用率超过 40% 时，模型推理质量明显下滑。**
> —— Harness Engineering 综合研究

这意味着 200k token 的窗口，**实际有效空间只有 ~80k**。超过后会出现：
- **上下文腐烂（Context Rot）**：Transformer 的 n² 注意力计算导致长上下文中信息召回能力下降
- **决策漂移**：早期指令和约束被后来的大量工具输出"淹没"
- **循环陷阱**：Agent 反复编辑同一文件、重复搜索相同内容

### 1.2 你的场景特有因素

根据 MEMORY.md 中的工作模式，以下是可能的上下文膨胀来源：

| 膨胀来源 | 典型场景 | 估算 token 消耗 |
|---------|---------|----------------|
| **CLAUDE.md / Rules 基线** | 5个 Rules + MEMORY.md + 系统提示 | 15-25k（启动即占用） |
| **MCP 工具描述** | iwiki / km / dayu-material 等 | 10-20k（工具集越多越重） |
| **大文件读取** | 读取 analysis.go / PRD / HTML Demo | 单次 5-30k |
| **多轮工具调用累积** | 搜索→读取→编辑→验证循环 | 每轮 3-8k，10轮 = 30-80k |
| **数据分析输出** | Plotly 图表代码 + 数据处理 | 单次 10-40k |
| **Web 搜索 + 抓取** | 深度调研模式 | 每个网页 3-10k |

**保守估算**：一个中等复杂任务启动后，基线 + 3-5 轮工具调用就可能触及 40% 阈值（~80k）。

## 2. Harness Engineering 五层解决方案

### 2.1 🏗️ 第一层：上下文架构——精准控制输入

**核心原则：不是让模型看更多，而是让模型只看必要的。**

#### A. CLAUDE.md 精简（已有基础，需优化）

```
目标：CLAUDE.md 总量 ≤ 2000 tokens
当前状态：MEMORY.md ~160行，需评估实际 token 量
```

**优化建议：**
- ✅ 只记录 Claude **经常犯错的内容**（你的"关键教训"部分很好）
- ❌ 不放项目详情（应按需读取）
- ❌ 不放完整工作流描述（应在 Skills / Rules 中）
- 📐 活跃项目部分改为**指针式**：只保留项目名+路径+一句话状态，详情让 Agent 按需读取

**改造示例：**
```markdown
## 活跃项目（按需读取详情）
| 项目 | 路径 | 状态 |
|------|------|------|
| 王也NPC | 10_Work/uc 王也 npc/ | Ready for Kick-off |
| UC对局复盘 | 10_Work/uc对局复盘/ | 迭代调优中 |
| 峡谷猫格 | 10_Work/lolm峡谷猫格/ | PRD+Demo完成 |
...
```
→ 从 ~50 行详情压缩到 ~10 行指针，**预估节省 3000-5000 tokens**

#### B. 延迟加载（Lazy Loading）

**原则：Agent 不预加载所有数据，仅维护轻量标识符，运行时按需拉取。**

```
当前问题：启动时加载 MEMORY.md 全文 + 5个Rules描述
改进方向：
  1. MEMORY.md → 极简启动版（用户+教训+项目指针）
  2. 项目详情 → Agent 工作时才读取对应 _README.md
  3. Rules → 已是 requested 类型（✅ 正确做法）
```

#### C. 结构化上下文

使用 XML 标签明确区分不同类型的信息，帮助模型高效定位：
```xml
<project_context>项目相关信息</project_context>
<task_spec>当前任务规格</task_spec>
<constraints>约束和限制</constraints>
```

### 2.2 🔄 第二层：上下文生命周期管理

**社区共识：在 60k tokens 或 30% 上下文使用率时主动清理，不要等到上限。**

#### A. Document & Clear 模式（强烈推荐 ⭐）

这是对抗上下文爆炸最有效的战术：

```
步骤：
1. 任务进行到中段（感觉开始变慢/质量下降）
2. 让 Agent 将当前进度写入 [任务名]-progress.md
   - 已完成的决策和结论
   - 未完成的待办事项
   - 关键文件路径和修改记录
3. 执行 /clear 清空上下文
4. 新会话中读取 progress.md 继续工作
```

**适用你的场景：**
- 数据分析任务（读数据→处理→可视化→报告 = 4个阶段，每阶段一次 clear）
- H5 Demo 开发（PRD解读→框架搭建→功能实现→视觉优化 = 分阶段）
- 深度调研（搜索收集→交叉验证→结构化报告 = 自然分段）

#### B. 上下文健康监控

建立直觉判断上下文健康度：

| 信号 | 含义 | 行动 |
|------|------|------|
| 响应变慢 | 可能接近上下文限制 | 准备 Document & Clear |
| 重复搜索同一内容 | 上下文腐烂，早期信息被遗忘 | 立即 Clear |
| 忘记之前的约束 | 系统提示被淹没 | 立即 Clear |
| 工具调用超过 10 轮 | 累积 token 过多 | 评估是否需要 Clear |

#### C. 关于 /compact 的建议

> **社区共识：避免依赖 /compact。** 自动压缩不透明、容易丢失关键信息、优化不佳。
> 手动 Document & Clear 更可控可靠。

### 2.3 🤖 第三层：子代理委派（Context Isolation）

**Anthropic 官方推荐：子代理可以进行深度探索（消耗大量 Token），但只向主代理返回精简摘要（1,000-2,000 Token）。**

#### A. 适用场景

| 任务类型 | 是否适合委派 | 原因 |
|---------|------------|------|
| 代码库搜索/探索 | ✅ 强烈推荐 | 搜索过程消耗大量 token，只需要结果 |
| 文件批量读取 | ✅ 推荐 | 避免大量文件内容污染主上下文 |
| 独立子功能实现 | ✅ 推荐 | 实现细节不需要回流到主代理 |
| 数据分析 | ⚠️ 视情况 | 简单分析不需要，复杂分析可拆分 |
| 需要全局上下文的决策 | ❌ 不适合 | 子代理缺乏完整项目上下文 |

#### B. 两种模式选择

**Master-Clone 模式（推荐默认使用）：**
- 主代理用 `Task(...)` 生成自身的克隆
- 所有上下文通过 CLAUDE.md 自动继承
- 灵活、简单、上下文连贯

**专业子代理模式（特定场景）：**
- code-explorer：代码库探索
- code-reviewer：代码审查
- comprehensive-researcher：深度调研
- 适用于已有明确分工的流水线

#### C. 实操建议

```
# 当你感觉任务会很重时，主动要求使用子代理
示例指令：
"用子代理搜索整个项目中关于 XXX 的实现，只返回关键结论"
"把这个 HTML 的样式优化委派给子代理，我只关心最终效果"
"让子代理读取这 5 个文件并总结关键信息"
```

### 2.4 📝 第四层：持久化记忆（你已有良好基础 ✅）

**核心原则：保留决策结论，丢弃推理过程。**

你的记忆系统（`.codebuddy/memory/`）已经实现了这一层，但可以进一步优化：

#### 优化建议

| 当前做法 | 优化方向 |
|---------|---------|
| MEMORY.md 包含项目详情 | → 项目详情移到 semantic/context.md，MEMORY.md 只保留指针 |
| episodic 日志记录做了什么 | → ✅ 保持（已很好） |
| working/current.md 跨会话 | → ✅ 保持（已很好） |
| 无任务中间状态文件 | → 新增 `working/[task]-progress.md` 支持 Document & Clear |

#### 知识沉淀闭环

```
发现宝贵信息（如构建命令、调试技巧、数据口径）
    ↓
写入持久记忆库（procedural/skills.md 或 semantic/context.md）
    ↓
下次会话自动可用，无需重复探索
    ↓
减少上下文中的重复搜索和工具调用
```

### 2.5 ⚙️ 第五层：工具与 MCP 治理

**社区警告：MCP 超过 20k tokens 会严重削弱 Claude 的能力。**

#### 当前 MCP 状态评估

你配置了 `iwiki`、`km`、`dayu-material` 三个 MCP 服务器，每个都有大量工具：
- iwiki：27+ 个工具
- km：16+ 个工具
- dayu-material：24+ 个工具

**每个工具的描述都会消耗 token，即使你不使用它们。**

#### 优化建议

| 建议 | 说明 |
|------|------|
| 评估常用工具 | 统计过去 2 周实际使用的 MCP 工具，保留高频，移除低频 |
| 按需连接 | 不需要 MCP 的任务，考虑是否可以临时关闭部分 MCP |
| 工具描述精简 | 确保工具描述简洁，避免冗长的参数说明 |
| CLI 替代 | 无状态工具考虑简化为 CLI 命令，在 Skills 中记录用法 |

## 3. 实操 SOP：防止上下文爆炸的标准流程

### 3.1 任务启动前

```
□ 评估任务复杂度（简单/中等/复杂）
□ 简单：直接做，不需要特殊管理
□ 中等：准备 Document & Clear 的断点
□ 复杂：规划子代理分工 + 多阶段 Clear
```

### 3.2 任务执行中

```
□ 每 5-8 轮工具调用后，自检上下文状态
□ 感觉响应变慢 → 准备 Document & Clear
□ 搜索/读取密集型操作 → 委派给子代理
□ 发现有价值的信息 → 立即写入持久记忆（不等会话结束）
```

### 3.3 任务阶段切换时

```
□ 阶段完成 → 让 Agent 输出阶段总结到文件
□ /clear 清空上下文
□ 新会话读取总结文件 + CLAUDE.md 继续
```

### 3.4 任务完成后

```
□ 写入 episodic 日志
□ 有价值的发现 → 写入持久记忆
□ 清理 working/ 中的中间文件
```

## 4. 针对你常见任务类型的具体策略

### 4.1 数据分析任务

```
阶段1: 数据理解（读取数据+探索）→ 子代理做探索，返回数据概要
       → Clear
阶段2: 数据处理（清洗+计算）→ 主代理执行，产出中间结果到文件
       → Clear
阶段3: 可视化（Plotly 图表）→ 主代理生成图表代码
       → Clear
阶段4: 报告整合 → 读取前面产出的文件，整合成最终报告
```

### 4.2 H5 Demo 开发

```
阶段1: PRD 解读 + 框架搭建 → 产出骨架 HTML
       → Clear
阶段2: 功能实现（逐个功能用 replace_in_file）→ 每 3-4 个功能 Clear 一次
       → Clear
阶段3: 视觉升级 + 打磨
```

### 4.3 深度调研

```
阶段1: Web搜索 + 网页抓取 → 子代理并行搜索，汇总到 md 文件
       → Clear
阶段2: 交叉验证 + 结构化 → 读取汇总文件，产出报告
```

### 4.4 PRD / 需求文档

```
阶段1: 背景调研 + 竞品分析 → 子代理搜索，汇总关键信息
       → Clear
阶段2: 文档撰写（结论→结构→内容）→ 主代理写入文件
       → Clear
阶段3: 分级审查（中等级以上自动触发对立角色审查）
```

## 5. 快速参考卡片

### 上下文爆炸的 5 个红灯信号 🚨

1. **响应时间明显变长**（正常 3-5s → 10s+）
2. **Agent 忘记之前说过的话**（重复问已回答的问题）
3. **Agent 开始重复搜索同一内容**
4. **输出质量突然下降**（遗漏细节、格式混乱）
5. **工具调用已超过 10 轮**

### 上下文管理 5 条铁律

1. **40% 就是上限** → 200k 窗口只用 80k
2. **Document & Clear > /compact** → 手动可控优于自动黑箱
3. **搜索/读取 → 子代理** → 探索过程不污染主上下文
4. **结论→文件，过程→丢弃** → 持久化有价值的，释放临时的
5. **MCP ≤ 20k** → 工具集不是越多越好
