Part 2 · Sub-Agents

并行加速

Sub-Agents = 你是项目经理，同时派 3 个人去做不同的调研，他们各自回来汇报。

核心优势：并行 + 隔离。每个 Sub-Agent 独立工作，不会互相干扰。

📐 核心设计原则

  • 最小化通讯：任务分发时一次性给全所有必要信息
  • 最大化自治：每个 Agent 能独立完成任务，不需频繁请示

⚠️ 为什么这样设计？

  • 上下文爆炸：Sub-Agent 同时返回结果，会撑爆主 Agent 的上下文窗口
  • 注意力稀释：通讯越多，信息损耗越大，关键信息容易被淹没

用法一 · 模拟用户

让 AI 扮演不同段位玩家

场景：海克斯大乱斗符文推荐——设计完推荐逻辑后验证是否合理

🟢

新手玩家

看不懂符文，需要直接告诉"选哪个"

🟡

中等玩家

理解基础机制，想知道"为什么推荐"

🔴

高手玩家

自己有判断，推荐不准会降低信任

发现关键设计缺陷 🚨

最初设计：强制"3 选 1 分布"——一定有一个推荐、一个一般、一个不推荐。

模拟后发现：如果 3 张符文都很好，强制降级会让高手觉得"推荐不专业"。

最终改为 → 独立评分制：3 张都好就都推荐，3 张都差就都建议刷新。
💡

模拟用户不能替代真实用研，但可以在方案定稿前就发现明显的逻辑硬伤。

深度解析

为什么要最小化通讯？

无论 Sub-Agent 还是 Agent Team，都遵循同一原则

💥

问题一：上下文爆炸

当多个 Sub-Agent 同时返回结果给主 Agent 时，回传内容会累积进主控的上下文窗口

Agent A 返回 280 行报告
Agent B 返回 970 行报告
Agent C 返回 340 行报告
主控累计 ≈ 1,590 行 → 💥 上下文爆炸
上下文 ≥ 40% 时，推理质量明显下滑
🔍

问题二：注意力稀释

通讯过程中会造成信息损耗，关键指令容易被淹没在海量内容中

Lost in the Middle 效应：
大模型对上下文中间部分的注意力最弱，早期指令容易被后来的大量输出「挤掉」
每次通讯消耗 2 个 turn（一发一收）
💡

核心应对策略：① 要求 Agent 返回摘要而非全文，详细内容写入文件 ② 控制单批并行 Agent ≤ 3 个 ③ 任务分发时一次性给全信息，让 Agent 自给自足。

本地实践

PRD 的角色重新定位

PRD 不会消失，但从「施工图纸」退化为「决策备忘录」

PRD 保留的 原型承担的
定位 Why — 为什么做（背景、目标、指标） What — 做成什么样（界面、交互、流程）
决策 决策记录 — 为什么选方案 A 不选 B 体验验证 — 方案 A 实际用起来如何
范围 边界条件 — 异常情况怎么处理 主流程演示 — 正常路径长什么样
PM 能力 ⬇️ 下降
  • 文档撰写能力
PM 能力 ⬆️ 上升
  • 问题定义能力
  • 快速验证能力
  • AI 工具驾驭能力
💡

原型是更好的思考工具——文字只能传递逻辑，原型才能传递体感。用「做」来想，比用「写」来想更快发现问题。

Part 4 · Superpowers Skills

AI 开发够快了，真正该花时间的是动手之前

我的真实感受：

AI 帮你写代码、搭服务已经够快了。真正该花时间的地方，是动手之前——

你需要不断地被拷打、不断地跟团队分析所有的边界情况，
还必须有老师傅坐镇把关，最后才能出来一个真正能向用户交付的东西。
💡

说回 Superpowers——

上面的所有这些（被拷打、分析边界、老师傅把关），其实都还只是 Superpowers 流程中的第一个 Skill——
也就是 brainstorming（头脑风暴）。

而 brainstorming 只是第一步，后面还有 规划 → 并行开发+自动审查 → 验证 的完整链路

Skill #1 · 最关键的一步

brainstorming：动手前的灵魂拷问

它不是简单的"发散创意"，而是一套结构化的需求审查流程

🔍 它会做什么？

  • 逼你把模糊的想法说清楚
  • 追问边界条件和异常情况
  • 模拟不同角色质疑你的方案
  • 生成多个备选方案进行对比
  • 评估技术可行性 & 用户体验

🎯 实战案例

异人体检站：
从 1 个想法 → 12 个创意方向 → 最终选定 3 个可行方案
以铲换铲：
评分维度怎么定？作弊图片怎么处理？VLM 不稳定怎么兜底？
——这些全在 brainstorming 阶段就被挖出来了
这就像「老师傅坐镇」：

你提一个方案，AI 会不断追问——"如果用户传了不是铲子的图呢？""如果 VLM 返回超时怎么办？""你有没有考虑并发情况？"

被拷打完的方案，才是真正能交付的方案。

完整流程

四步闭环：从拷打到交付

Superpowers 不是一个 Skill，而是一套环环相扣的工作流

1

🧩 brainstorming

被拷打阶段——探索意图、挖掘边界、老师傅审查

花 80% 的思考时间在这一步
2

📋 writing-plans

规划阶段——把审查通过的方案拆解为可执行步骤

以铲换铲 AI 评分方案规划
3

⚡ subagent-driven-development

开发阶段——并行执行计划 + 自动代码审查

每完成一个子任务 → 自动触发 code-reviewer 审查
不是"写完再查"，是"边写边审"
4

✅ verification-before-completion

验证阶段——完成前强制验证，不做空口承诺

VLM 评分精度验证闭环
🧩 被拷打 → 📋 出计划 → ⚡ 边写边审 → ✅ 强制验收
💡

上面整个链路最关键的洞察：动手之前花的时间 ≫ 动手之后。AI 写代码只要几分钟，但 brainstorming + writing-plans 可能要花一个下午——这才是真正决定交付质量的地方。

展望 · PM 新定位

边界上的验证者

产品经理的新定位：多做一些边界上的验证。

不是要全栈闭环一整个需求、直接对接项目组开发——而是把那些 Demo 性质的、有边界限制的工作，用 AI 来快速验证、快速迭代。
🧪

及时验证"可能有用"的需求

心里有很多需求，觉得可能有用，但又不确定要不要走正式流程？

→ 用 AI 快速验证，让想法在几小时内变成可触摸的原型，
而不是停留在"我觉得可以"的阶段。

🧭

培养"判断模型边界"的直觉

当 AI 报错或结果不如预期时，要分辨：

❶ 模型理解错了？
❷ 上下文给得不够？
❸ 这件事本来就做不到？

💡

多做尝试，哪怕会失败、会有 bug——失败本身就是理解模型边界的机会。
当我们真正理解了这个边界，自身对 AI 的理解会加深，产品直觉也会变得更强。

拓宽模型的边界认知 = 拓宽产品经理自身的边界。

"AI 不是让产品经理变成超人，
而是让产品经理少走弯路——

提前体验、多角度评估、快速验证。"
