Part 2 · Agent Teams

多视角协作

Agent Teams = 一间虚拟会议室，你坐在里面，同时有产品经理、技术 Lead、QA、项目经理各自发表意见。

不是一个人对着 AI 来回聊，而是多个角色同时从各自的职责出发工作。

创作逻辑 · 从临时构建到沉淀复用

两条路径

⚙️

路径一：临时构建

AI 根据 Prompt 自动创建子 Agent，并让它去写代码以实现特定功能。

📝 用户给出需求 → AI 拆分任务
🤖 自动派生 Sub-Agent → 各自执行
📦 汇总结果 → 交付产出
🎨

路径二：沉淀为 Rules 和内置子 Agent

针对常用场景，把 Agent 的角色定义沉淀下来，而不是每次依赖临时构建。

📜 写入 Rules：行为准则、评审标准、输出格式固化为项目级/全局 Rules，AI 启动时自动加载
🤖 配置内置子 Agent：code-reviewer、data-analyst 等高频角色，带专属 system prompt 和工具权限

🏷️ 涵盖多种职业角色

PM 开发 前端 QA 设计 数据分析 …更多

每个细分职业下都有不同具体执行项的 Agent

💡

核心思路：从"即用即造"到"预制件装配"——把反复验证过的角色定义沉淀为 Rules 和内置子 Agent，实际工作时像搭积木一样组合。沉淀的质量决定了协作的上限。

Part 3 · Sub-Agents

不只是并行

Sub-Agents = 你是项目经理，同时派 3 个人去做不同的调研，他们各自回来汇报。

很多人以为 Sub-Agent 只是"同时干几件事更快"。实际上，它的价值远不止并行——
🚀

① 并行加速

3 个调研任务同时跑，时间从串行的 3 倍缩短到 ~1 倍

适合互不依赖的任务
🧊

② 上下文隔离

每个 Sub-Agent 有独立的上下文窗口，主 Agent 只接收汇总摘要

最重要的价值 ⭐
🎯

③ 专注度提升

每个 Sub-Agent 只面对一个明确任务，避免"Lost in the Middle"效应

任务越专注，输出越高质量
💡

Sub-Agent 不只是"更快"，更是"更清醒"——每个 Agent 都在自己的干净房间里工作，最终只把结论拿出来汇报。

设计原则

为什么要最小化通讯？

📐 两条铁律

  • 最小化通讯：任务分发时一次性给全所有必要信息
  • 最大化自治：每个 Agent 能独立完成任务，不需频繁请示

⚠️ Lost in the Middle 效应

大模型对上下文开头和结尾关注度最高，对中间部分注意力最弱。

📌 早期指令 ← 注意力高
📦 Sub-Agent A 返回大段结果
📦 Sub-Agent B 返回大段结果 ← 注意力最弱
📌 最新指令 ← 注意力高

通讯越多 → 中间堆积越多 → 关键信息越容易被"看不见"

💡

应对策略：① 要求 Agent 返回摘要而非全文，详细内容写入文件 ② 控制单批并行 Agent ≤ 3 个 ③ 任务分发时一次性给全信息，让 Agent 自给自足——减少中间堆积，让关键信息不被淹没。

用法一 · 模拟用户

让 AI 扮演不同段位玩家

场景：海克斯大乱斗符文推荐——设计完推荐逻辑后验证是否合理

🟢

新手玩家

看不懂符文，需要直接告诉"选哪个"

🟡

中等玩家

理解基础机制，想知道"为什么推荐"

🔴

高手玩家

自己有判断，推荐不准会降低信任

发现关键设计缺陷 🚨

最初设计：强制"3 选 1 分布"——一定有一个推荐、一个一般、一个不推荐。

模拟后发现：如果 3 张符文都很好，强制降级会让高手觉得"推荐不专业"。

最终改为 → 独立评分制：3 张都好就都推荐，3 张都差就都建议刷新。
💡

模拟用户不能替代真实用研，但可以在方案定稿前就发现明显的逻辑硬伤。这里 Sub-Agent 的价值不是并行，而是角色隔离——每个"用户"都沉浸在自己的段位视角里。

用法二 · 并行调研

3 个 Agent 同时处理数据

场景：搭建海克斯大乱斗数据体系，需要同时处理多个数据源

📊

数据分析 Agent

英雄 × 符文胜率分析

30,503 条数据
🧩

组合分析 Agent

符文组合协同效应

20,328 条 → 527 个唯一组合
📚

知识整理 Agent

黑科技组合 & 知识库

结构化知识库
💡

这个场景同时体现了三重价值——并行让 3 个分析同时进行；隔离让每个 Agent 各自处理 2-3 万条数据而不互相干扰；专注让每个 Agent 只关心自己的分析维度，输出质量更高。

一个启发

从文档到 Demo

✅ AI 擅长
  • 快速验证想法
  • 多角度评估方案
  • 生成草稿和原型
❌ AI 不擅长
  • 完全替代人做最终决策
  • 独立完成完整交付

💬 一个建议

像 Agent Teams 这种多 Agent 协同架构，很适合给它一个模糊的命题让它自己去跑、去探索。
现在每个人的 Token 量非常多，大多数同学其实用不完——给 AI 一个你想了解的方向，让它帮你完成闭环，做一些边界上的尝试。

本地实践

PRD 的角色重新定位

PRD 不会消失，但从「施工图纸」退化为「决策备忘录」

PRD 保留的 原型承担的
定位 Why — 为什么做（背景、目标、指标） What — 做成什么样（界面、交互、流程）
决策 决策记录 — 为什么选方案 A 不选 B 体验验证 — 方案 A 实际用起来如何
范围 边界条件 — 异常情况怎么处理 主流程演示 — 正常路径长什么样
💡

原型是更好的思考工具——文字只能传递逻辑，原型才能传递体感。用「做」来想，比用「写」来想更快发现问题。

金铲铲「以铲换铲」活动——AI 图片评分的原型之路

业务提需求 → AI 搭离线 Demo → 给业务体验 → AI 搭在线服务 → 项目组接入

展望 · PM 新定位

边界上的验证者

🛠️

Demo 性质的工作，自己就能做

那些 Demo 性质的、有边界的工作——快速原型、效果验证、方案对比——完全可以用 AI 来快速验证、快速迭代。

这一块不依赖算法同学或开发同学，产品经理自己就能推动。

🧭

培养"判断模型边界"的直觉

当 AI 报错或结果不如预期时，要分辨：

❶ 模型理解错了？
❷ 上下文给得不够？
❸ 这件事本来就做不到？

💡

多做尝试，哪怕会失败、会有 bug——失败本身就是理解模型边界的机会。
当我们真正理解了这个边界，产品直觉也会变得更强。

"用原型替代文档，
用体验替代讨论，
用做来想，比用写来想更快发现问题。"
