## 开场：我为什么要分享这个？（~2 min）

最近半年做了几个 AI 相关的产品项目，想分享三个典型 Case：

- 🎭 **《一人之下》异人体检站**——结合营销活动，用 Superpowers 发散 Idea，让 Agent Teams 中不同角色分别出方案，积累的职业 Skills 帮我产出多维度方案
- ⚔️ **《金铲铲之战》以铲换铲**——产品经理不再只做离线 Demo，AI 可以部署在线服务，让项目组接入 LLM 真实体验不同输入输出的效果
- 🤖 **Agent Teams & Sub-Agents**——多个 Agent 带入不同角色，AI 自问自答快速生成示例；也可让产品带入不同角色体验后给出建议

> ⚠️ 实践发现：一次性开启太多 Sub-Agent，很容易出现**上下文爆炸**的情况。

在做这些项目的过程中，我发现 AI 工具对产品经理工作方式的改变，比我预想的要大得多。今天不讲技术细节，聊聊**工具怎么改变了做事的方式**。

## 一、Agent Teams：多视角协作（~8 min）

### 1.1 一句话解释

Agent Teams = **一间虚拟会议室**，你坐在里面，同时有产品经理、技术 Lead、QA、项目经理各自发表意见。

不是一个人对着 AI 来回聊，而是多个角色同时从各自的职责出发工作。

### 1.2 创作逻辑：从自动创建到前置定制

Sub-Agent 和 Agent Teams 的创作逻辑可以分为两条路径：

**路径一：自动创建与执行**
- AI 根据 Prompt 自动创建子 Agent，并让它去写代码以实现特定功能
- 流程：用户给出需求 → AI 拆分任务 → 自动派生 Sub-Agent → 各自执行 → 汇总结果

**路径二：前置定制与输入**
- 我们可以前置地给 AI 输入：在 Claude Code 里定制 Sub-Agents，同时调用 Skills（Agency Agents）
- 涵盖多种职业角色：PM、开发、前端、QA、设计、数据分析…每个细分职业下都有不同具体执行项的 Agent
- 根据自己的工作项找到合适的 Agent → 将其属性**切成 Role** 并保存 → 碰到实际任务时**直接调用**预设好的 Agent

> 💡 核心思路：从"即用即造"到"预制件装配"——提前准备好角色定义，实际工作时像搭积木一样组合，效率远高于每次从零开始。

### 1.3 案例一：异人体检站 PRD 多角色评审

**做法**：组了一支 4 人 AI 团队，同时评审同一份 PRD——

| 角色 | 评审焦点 | 产出亮点 |
|------|----------|----------|
| 🧑‍💼 产品经理 | 用户价值、体验流程 | 发现体验链路过长 |
| 👨‍💻 技术 Lead | 架构、接口、性能 | 标记 3 个 Critical 风险 |
| 🧪 QA | 测试覆盖、边界 Case | 产出 ~450 条用例 |
| 📋 项目管理 | 排期、资源、风险 | 拆解 73 个可执行任务 |

**结果**：
- 不到 2 小时，一次性产出 **9 份完整文档**
- 发现排期严重低估（5-6 周 → 建议 8-9 周）
- 人工做这套评审，至少 1-2 周

**💡 体会**：多角色的价值在于**打破盲区**——产品觉得"体验流畅"的地方，技术说"有性能风险"，QA 说"边界 Case 没考虑"。

### 1.4 案例二：创意脑暴

**做法**：用 Superpowers 的 brainstorming skill，让 Agent 从 4 个视角发散——

| 视角 | 关注点 | 产出示例 |
|------|--------|----------|
| IP 粉丝 | 什么让老粉兴奋？ | 甲申之乱推演、角色面试官 |
| 新玩家 | 什么降低门槛？ | 异人鉴定局、体检报告 |
| 传播 | 什么让人自发分享？ | 算命摊、败犬语录 |
| 技术 | 什么能复用现有能力？ | 一鱼三吃策略 |

**结果**：12 个创意 → 筛选 Top 5 → 收敛为"最小组合拳"方案。

**💡 体会**：脑暴的核心不是"AI 帮你想"，而是"AI 从**你想不到的角度**帮你想"。一个人容易陷入路径依赖。

## 二、Sub-Agents：并行加速（~7 min）

### 2.1 一句话解释

Sub-Agents = **你是项目经理，同时派 3 个人去做不同的调研**，他们各自回来汇报。

核心优势：**并行 + 隔离**。每个 Sub-Agent 独立工作，不会互相干扰。

### 2.2 核心设计原则

所有的 Sub-Agent 和 Agent Teams 都遵循两条铁律：

1. **最小化通讯**：任务分发时一次性给全所有必要信息
2. **最大化自治**：每个 Agent 能独立完成任务，不需频繁请示

**为什么这样设计？**

- **上下文爆炸**：当 Sub-Agent 同时返回结果给主 Agent 时，回传内容会累积进主控的上下文窗口。研究表明上下文利用率超过 40% 时推理质量明显下滑（200k 窗口实际有效空间只有 ~80k）
- **注意力稀释**：通讯过程中会造成信息损耗。大模型存在 "Lost in the Middle" 效应——对上下文中间部分的注意力最弱，早期指令容易被后来的大量输出「挤掉」

**应对策略**：① 要求 Agent 返回摘要而非全文，详细内容写入文件 ② 控制单批并行 Agent ≤ 3 个 ③ 任务分发时一次性给全信息，让 Agent 自给自足

### 2.3 用法一：模拟用户

**场景**：海克斯大乱斗符文推荐——设计完推荐逻辑后，需要验证是否合理。

**做法**：让 Sub-Agent 分别扮演不同段位的玩家，体验推荐结果——

- 🟢 **新手**：看不懂符文，需要直接告诉"选哪个"
- 🟡 **中等**：理解基础机制，想知道"为什么推荐"  
- 🔴 **高手**：自己有判断，推荐不准会降低信任

**发现了一个关键设计缺陷**：

> 最初设计是"强制 3 选 1 分布"——一定有一个绿（推荐）、一个黄（一般）、一个灰（不推荐）。
> 
> 但模拟后发现：如果 3 张符文确实都很好，**强制降级会让高手觉得"推荐不专业"**。
> 
> 最终改为**独立评分制**：3 张都好就都推荐，3 张都差就都建议刷新。

**💡 体会**：模拟用户不能替代真实用研，但可以**在方案定稿前**就发现明显的逻辑硬伤。

### 2.4 用法二：并行调研

**场景**：搭建海克斯数据体系，需要同时处理多个数据源。

**做法**：并行派出 3 个 Sub-Agent——

| Sub-Agent | 任务 | 数据量 |
|-----------|------|--------|
| 数据分析 | 英雄×符文胜率分析 | 30,503 条 |
| 组合分析 | 符文组合协同效应 | 20,328 条 → 527 个唯一组合 |
| 知识整理 | 黑科技组合 & 知识库 | 结构化知识库 |

**💡 体会**：并行的好处不只是"快"，更重要的是**减少上下文污染**——每个 Agent 各自探索，最终只汇总结果，主 Agent 的"大脑"保持清爽。

## 三、认知转变：从文档到 Demo（~8 min）

### 3.1 行业印证：Anthropic 的原型先行方法论

最近 Anthropic 的 Claude Code 团队分享了他们的产品方法，和我们的实践不谋而合：

> **"我们不需要完美的计划，我们需要的是快速的反馈。"** —— Cat Wu

**四步打造高效产品反馈循环**：

1. **Prototype-first**：不再优先写长文档，而是优先做 Demo。一个 PM 可以在一个下午从 Idea 变成 Working Prototype
2. **真实反馈驱动**：让内部用户直接试用，获得真实 Engagement。押错方向的成本很低
3. **Evals 优于抽象讨论**：设计 Evals 衡量 Feature 是否有效。例如 Agent Teams 功能专门设计了评估体系
4. **Demo 和 Evals 优于 Docs**：团队不再举行传统 Stand-up，而是分享新想法的 Demo

**PRD 角色重新定位**：PRD 不会消失，但从「施工图纸」退化为「决策备忘录」：

| PRD 保留的 | 原型承担的 |
|-----------|-----------|
| **Why** — 为什么做（背景、目标、指标） | **What** — 做成什么样（界面、交互、流程） |
| **决策记录** — 为什么选方案 A 不选 B | **体验验证** — 方案 A 实际用起来如何 |
| **边界条件** — 异常情况怎么处理 | **主流程演示** — 正常路径长什么样 |

**💡 体会**：原型是更好的思考工具——文字只能传递逻辑，原型才能传递体感。用「做」来想，比用「写」来想更快发现问题。

### 3.2 一个启发

最近读到一篇 Claude 员工的博客，讨论他们自己怎么用 AI。核心观点：

> **AI 更适合做"探索性"的事，不适合让它去"闭环"所有事。**

- ✅ 适合：快速验证想法、多角度评估方案、生成草稿和原型
- ❌ 不适合：完全替代人做最终决策、独立完成完整交付

这和我的实践感受一致——Agent Teams 和 Sub-Agents 在**探索和评估**环节价值巨大，但最终的产品判断和取舍，还是需要人来做。

### 3.3 产品经理工作方式的变化

这个认知落到产品经理的日常工作上，最大的变化是：

**以前**：想法 → 写文档 → 交开发 → 上线 → 看数据 → 发现问题 → 返工

**现在**：想法 → 写文档 → **快速搭 Demo** → **亲自体验** → 修改文档 → 交开发

```
发现问题的成本：
  传统：几周开发 + 返工     💸💸💸
  现在：几小时搭 Demo       💰
```

### 3.4 案例：以铲换铲——从离线 Demo 到在线服务

**背景**：金铲铲之战「以铲换铲」活动——玩家上传自制铲子照片，AI 实时评分。

**以产换产的原型之路**：

```
业务提需求 → AI 搭离线 Demo → 给业务体验 → AI 搭在线服务 → 项目组接入
```

**Step 1：离线 Demo**
- 用 AI 快速搭了一个**本地 Gradio 应用**——上传图片 → VLM 评分 → 展示等级和评语
- 让业务第一时间看到「AI 识别铲子」到底靠不靠谱

**Step 2：在线服务**
- 发现 AI 还能帮我搭**完整的后端服务**——接口 + 日志 + 并发处理
- 让项目组直接在线调用，体验真实推理效果

**关键转变**：
- 传统流程：PM 写 PRD → 等开发排期 → 几周后才能看到效果
- 现在：PM **当天搭出可运行的 Demo**，业务马上体验
- 意外收获：AI 不止帮我做了原型，还帮我搭了一套**可以给项目组用的在线服务**

> **以产品原型换取项目推动力——「以产换产」**

### 3.5 核心认知

| 维度 | 以前 | 现在 |
|------|------|------|
| 验证方式 | 写完文档 → 开发完再验证 | 写完文档 → **搭 Demo 先验证** |
| 方案探索 | 一个方案写到底 | **同时探索多个方向**，选最优 |
| 评审方式 | 开会讨论 | **AI 预评审** → 带着问题再开会 |
| 数据分析 | 等分析师排期 | **自己先做初步分析** |

这不是在替代产品经理，而是让产品经理能做到**以前做不到的事**。

## 四、Superpowers：标准化工作流 Skills（~5 min）

### 4.1 核心感悟

**AI 来开发已经够快了，真正该花时间的地方是动手之前。**

你需要不断地被拷打、不断地跟团队分析所有的边界情况，还必须有老师傅坐镇和把关，最后才能出来一个真正能向用户交付的东西。

说回 Superpowers——上面这些（被拷打、分析边界、老师傅把关），**其实都还只是 Superpowers 流程中的第一个 Skill**，也就是 `brainstorming`（头脑风暴）。

### 4.2 Skill #1：brainstorming（最关键的一步）

brainstorming 不是简单的"发散创意"，而是一套**结构化的需求审查流程**：

**它会做什么？**
- 逼你把**模糊的想法**说清楚
- 追问**边界条件**和异常情况
- 模拟不同角色质疑你的方案
- 生成**多个备选方案**进行对比
- 评估技术可行性 & 用户体验

**实战案例**：
- **异人体检站**：从 1 个想法 → 12 个创意方向 → 最终选定 3 个可行方案
- **以铲换铲**：评分维度怎么定？作弊图片怎么处理？VLM 不稳定怎么兜底？——这些全在 brainstorming 阶段就被挖出来了

> 这就像「老师傅坐镇」：你提一个方案，AI 会不断追问——"如果用户传了不是铲子的图呢？""如果 VLM 返回超时怎么办？""你有没有考虑并发情况？"  
> **被拷打完的方案，才是真正能交付的方案。**

### 4.3 完整四步闭环：从拷打到交付

| 步骤 | Skill | 做什么 | 实战应用 |
|------|-------|--------|----------|
| ① 被拷打 | **brainstorming** | 探索意图、挖掘边界、老师傅审查 | 花 80% 思考时间在这一步 |
| ② 出计划 | **writing-plans** | 把审查通过的方案拆解为可执行步骤 | 以铲换铲 AI 评分方案规划 |
| ③ 边写边审 | **subagent-driven-development** | 并行执行计划 + 自动代码审查 | 每完成一个子任务 → 自动触发 code-reviewer |
| ④ 强制验收 | **verification-before-completion** | 完成前强制验证，不做空口承诺 | VLM 评分精度验证闭环 |

**`subagent-driven-development` 的特点**：不是"写完再查"，是"边写边审"。每完成一个子任务就自动触发 code-reviewer 审查，问题在早期就被拦截。

**💡 核心洞察**：动手之前花的时间 ≫ 动手之后。AI 写代码只要几分钟，但 brainstorming + writing-plans 可能要花一个下午——这才是真正决定交付质量的地方。

## 五、总结（~2 min）

### 四个工具，四个价值

| 工具 | 一句话价值 |
|------|-----------|
| **Agent Teams** | 多角色协作，打破单一视角盲区 |
| **Sub-Agents** | 并行加速，减少上下文污染 |
| **快速 Demo** | 原型先行，提前排雷 |
| **Superpowers** | 标准化 Skills，最佳实践复用 |

### 四个认知

1. **AI 适合探索，不适合闭环**——让 AI 帮你看到更多可能性，最终判断靠人
2. **多视角 > 单视角**——好评审不是"找更聪明的人"，而是"找更多不同角色的人"
3. **原型 > 文档**——文字只能传递逻辑，原型才能传递体感
4. **流程 > 能力**——好的 Skills 让每次执行都遵循最佳实践，不依赖个人发挥

### PM 新定位：边界上的验证者

产品经理的新定位：多做一些**边界上的验证**。这样从这个角度，也可以拓宽产品经理本身的边界。

这里并不是说产品经理要全栈闭环一整个需求、直接对接项目组开发。但那些 **Demo 性质的、有边界限制的工作**，完全可以用 AI 来快速验证、快速迭代。

**及时验证"可能有用"的需求**
- 心里有很多需求，觉得可能有用，但不一定非要走正式流程
- → 用 AI 快速验证，让想法在几小时内变成可触摸的原型

**培养"判断模型边界"的直觉**
- 当 AI 报错或结果不如预期时，要分辨：
  1. 模型理解错了？
  2. 上下文给得不够？
  3. 这件事本来就做不到？

> 💡 多做尝试，哪怕会失败、会有 bug——**失败本身就是理解模型边界的机会**。当我们真正理解了这个边界，自身对 AI 的理解会加深，**产品直觉也会变得更强**。拓宽模型的边界认知 = 拓宽产品经理自身的边界。

### 一句话

> **AI 不是让产品经理变成超人，而是让产品经理"少走弯路"——提前体验、多角度评估、快速验证。**
