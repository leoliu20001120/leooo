# AI Agent 架构深度调研：单 Agent、Sub-Agent 与 Agent Team 的选型指南

> 作者：刘思行（Leo）
> 创建时间：2026-03-23
> 文档定位：技术调研报告 · AI Agent 工程化实践

---

## TL;DR — 30 秒速览

> 选架构不是选框架，而是**回答「这个任务的协作形态是什么」**。

| 如果你的任务… | 选这个 | 一句话理由 |
|-------------|--------|----------|
| 单步 / 少步问答 | **单 Agent** | 简单即正义，不要过度工程 |
| 有明确先后依赖的流水线 | **Sub-Agent** | 流水线结构 = 树形调度 |
| 需要多视角审查或创意碰撞 | **Agent Team** | 横向通信 > 纵向调度 |
| 简单任务 + 少数复杂决策 | **混合架构** | 80% Sub-Agent + 20% Team |
| 不确定？ | **从单 Agent 起步** | 遇到瓶颈再演进 |

**核心洞察**：Sub-Agent 是「工程化确定性」的最优解，Agent Team 是「创造性探索」的最优解，生产级系统几乎都是两者的混合。

## 一、背景与动机

> 💡 **本章核心**：Agent 架构正在从「单体」走向「分布式」，但更多选择也意味着更容易选错。

随着 LLM 能力快速提升，AI Agent 从概念验证走向工程化落地。从单一 Prompt 问答到工具调用（Tool Use）、ReAct 循环，再到 Multi-Agent 协作体系——架构选择越来越丰富，**"该用哪种？"** 也越来越难回答。

本文旨在：

1. 清晰界定各类 Agent 架构的**本质定义与适用边界**
2. 深入对比 Sub-Agent 与 Agent Team 在**真实工程场景**中的优劣
3. 提炼面向实际项目的**选型决策框架**

---

## 二、架构演进：从单兵到军团

> 💡 **本章核心**：每个架构层级都是前一层能力不足时的自然延伸——理解这条路径，是合理选型的前提。

```
单 Agent（Single Agent）
    ↓  上下文不够用了
带工具调用的增强 Agent（Tool-Augmented Agent）
    ↓  需要多步动态决策
具备规划能力的 ReAct Agent（Plan + Act）
    ↓  单人干不完了
Sub-Agent 架构（主控 + 子 Agent，树形层级）
    ↓  需要对等讨论和多视角
Agent Team 架构（对等协作，网状通信）
    ↓  现实总是复杂的
混合架构（Hybrid Multi-Agent）
```

**关键认知**：不要跳级。如果 ReAct 单 Agent 能解决问题，引入 Multi-Agent 只会增加无谓的复杂度。

## 三、各类架构详解

### 3.1 单 Agent & ReAct：大多数时候够用了

> 💡 **核心观点**：80% 的 Agent 应用场景，单 Agent + 好的 Prompt 工程就能搞定。别急着上 Multi-Agent。

**单 Agent** 是一个 LLM 实例通过 Prompt 循环完成任务，可选配工具调用能力。**ReAct Agent** 在此基础上引入 Thought → Action → Observation 循环，实现多步动态推理。

```
User Task → [Thought] → [Action] → [Observation] → ... → Output
```

| 适用 | 不适用 |
|------|--------|
| 问答、翻译、内容生成 | 需要多种专业视角 |
| 单步 / 少步工具调用 | 大规模并行处理 |
| MVP 快速验证 | 超长上下文任务 |
| 流程固定的自动化 | 需要对抗性验证 |

**优势**：简单可控、延迟低、Token 消耗可预期、调试成本最低

**局限**：上下文窗口限制、串行执行无法并行、单 Agent 的专业深度有天花板

---

### 3.2 Sub-Agent 架构：让主控当「项目经理」

> 💡 **核心观点**：Sub-Agent 的本质是「分治法」——把大任务拆成互相独立的小任务，用树形结构调度。

**Orchestrator（主控 Agent）** 接收任务 → 分解 → 下发给专属 SubAgent 执行 → 收集结果 → 汇总输出。

```
User
 │
 ▼
┌─────────────────────────────────────────┐
│           Orchestrator Agent            │
│  - 任务理解与分解                         │
│  - SubAgent 调度与状态管理                │
│  - 结果聚合与输出                         │
└──────┬───────────┬───────────┬──────────┘
       │           │           │
       ▼           ▼           ▼
  SubAgent A   SubAgent B   SubAgent C
  (代码执行)   (网络搜索)   (文件操作)
       │           │           │
       └───────────┴───────────┘
                   │
             结果返回主控
```

#### 四条设计铁律

1. **职责单一**：每个 SubAgent 只做一件事，类似微服务
2. **无横向通信**：SubAgent 之间不直接交流，只通过主控中转
3. **上下文隔离**：每个 SubAgent 拥有独立的上下文窗口
4. **幂等性**：SubAgent 被重复调用应产生相同结果

#### 主流实现一览

| 框架 | 实现方式 | 特点 |
|------|---------|------|
| Claude Code | 工具调用式子 Agent | 深度集成代码执行环境 |
| LangGraph | 图节点式 Sub-Agent | 支持条件路由和循环 |
| AutoGen（层级模式） | GroupChat with Moderator | 灵活的对话管理 |
| CrewAI | Manager + Worker | 内置角色系统 |
| Google ADK | 树形 Agent 层级 | 原生支持多层 Sub-Agent |

#### 什么时候该选 Sub-Agent？

| 场景类型 | 具体案例 |
|---------|----------|
| **流水线任务** | 需求分析 → 代码生成 → 单测 → PR 创建 |
| **并行信息采集** | 同时爬取多个数据源后合并 |
| **工具专业化** | 代码 Agent + 搜索 Agent + 文件 Agent 各司其职 |
| **规模化工作流** | 大型文档处理、批量数据转换 |
| **受控自动化** | CI/CD 自动化、合规审查流水线 |

#### 优势与劣势

| ✅ 优势 | ❌ 劣势 |
|---------|--------|
| 关注点分离，各 SubAgent 可独立精调 Prompt | 主控 Orchestrator 是单点瓶颈 |
| 上下文隔离，SubAgent 只返回摘要给主控 | SubAgent 间无法直接协商，绕道主控增加开销 |
| 调用链清晰，出错可单独重试某个 SubAgent | 对于条件复杂的任务，调度逻辑可能成为维护难点 |
| 扩展性好，新增能力 = 新增 SubAgent | **多 SubAgent 回传结果累积，可能撑爆主控上下文**（详见 6.3 反模式四） |
| 可按任务复杂度分配不同大小的模型 | |

### 3.3 Agent Team 架构：让 Agent 们「开会讨论」

> 💡 **核心观点**：Agent Team 的价值不是「更多人干活」，而是「更多视角碰撞」——这也是它比 Sub-Agent 贵但在创造性任务上更强的原因。

多个 Agent 作为**平等成员**组成团队，Agent 之间可以**互相通信**，通过对话、辩论、角色扮演等方式协作。没有强制的中心控制节点。

```
User
 │
 ▼
┌──────────────────────────────────────┐
│              Agent Team              │
│                                      │
│  ┌──────────┐    ┌──────────┐        │
│  │ Agent A  │◄──►│ Agent B  │        │
│  │(产品经理) │    │(工程师)  │        │
│  └────┬─────┘    └────┬─────┘        │
│       │               │              │
│       ▼               ▼              │
│  ┌──────────────────────────┐        │
│  │       Agent C            │        │
│  │      (评审者)             │        │
│  └──────────────────────────┘        │
│                                      │
│  [共享消息总线 / 共享记忆]             │
└──────────────────────────────────────┘
 │
 ▼
Output（汇总/投票/共识）
```

#### 四种通信模式

| 模式 | 说明 | 适用 |
|------|------|------|
| **广播模式** | 所有 Agent 接收所有消息 | 讨论型任务（辩论、头脑风暴） |
| **点对点模式** | Agent 定向发送消息 | 审批流、接力型任务 |
| **黑板模式** | 共享内存/消息总线，Agent 主动读写 | 并行协作、知识共享 |
| **投票模式** | 多 Agent 各自判断后投票决策 | 质量评审、分类任务 |

#### 主流实现一览

| 框架 | 通信机制 | 特色 |
|------|---------|------|
| **MetaGPT** | 角色扮演 + 结构化输出 | 模拟软件公司工作流 |
| **CrewAI** | 角色分工 + 任务流 | 易上手，适合快速原型 |
| **AutoGen（对话模式）** | 多轮对话 | 灵活可定制 |
| **Microsoft Magentic-One** | Orchestrator + 专家 Agent | 通用任务型 Team |
| **AgentScope** | 流水线 + 消息总线 | 支持分布式部署 |

#### 什么时候该选 Agent Team？

| 场景类型 | 具体案例 | 推荐理由 |
|---------|---------|----------|
| **多视角决策** | 技术方案 PRD 评审 | 产品、技术、安全多角色交叉审阅 |
| **创意生成** | 广告语/游戏设计头脑风暴 | 多样性激发更丰富的创意 |
| **对抗性验证** | 代码安全审计、逻辑校验 | 攻防角色互相挑战 |
| **模拟协商** | 合同谈判预演、用研访谈模拟 | 角色扮演还原真实场景 |
| **知识综合** | 学术报告（文献综述 + 方法论 + 结论） | 分工专业化后合并 |
| **Workflow 自动化** | 软件开发全流程（PM→Dev→QA） | MetaGPT 典型用法 |

#### 优势与劣势

| ✅ 优势 | ❌ 劣势 |
|---------|--------|
| 无单点瓶颈，Agent 互补纠错 | 通信复杂度 O(n²)，Token 消耗急剧上升 |
| 并行能力强，多维度同时推进 | 共识难以达成，需要仲裁机制 |
| 涌现式质量提升（类似 Code Review） | 调试困难，需要完整的 Trace 系统 |
| 角色深度专业化（定制 System Prompt） | 不确定性高，可能走向意外分支或死循环 |
| 鲁棒性强，单 Agent 失败其他可接管 | 多轮通信累积延迟，不适合实时场景 |

## 四、核心对比矩阵

> 💡 **本章核心**：一张表看清三种架构的工程 Trade-off，帮助快速缩小选型范围。

### 4.1 架构特性对比

| 对比维度 | 单 Agent | Sub-Agent 架构 | Agent Team 架构 |
|---------|---------|----------------|----------------|
| **组织结构** | 独立个体 | 树形主从 | 网状对等 |
| **控制中心** | 自身 | Orchestrator | 无（或弱中心） |
| **通信复杂度** | 无 | O(n)，线性 | O(n²)，平方 |
| **任务并行度** | 低 | 中（可并行子任务） | 高 |
| **上下文管理** | 单一上下文 | 主控聚合，子 Agent 隔离 | 共享/分布式 |
| **错误恢复** | 重试自身 | 主控重调 SubAgent | Team 互补修复 |
| **延迟** | 最低 | 中 | 较高 |
| **Token 消耗** | 最低 | 中 | 最高 |
| **调试难度** | 低 | 中 | 高 |
| **扩展性** | 差 | 好（增减 SubAgent） | 中（增减成员影响协作） |
| **容错性** | 低 | 中 | 高 |

### 4.2 任务类型适配速查

| 任务类型 | 单 Agent | Sub-Agent | Agent Team |
|---------|---------|-----------|------------|
| 简单 QA | ⭐⭐⭐ | ⭐ | ⭐ |
| 单步工具调用 | ⭐⭐⭐ | ⭐⭐ | ⭐ |
| 多步骤流水线 | ⭐ | ⭐⭐⭐ | ⭐⭐ |
| 并行信息采集 | ⭐ | ⭐⭐⭐ | ⭐⭐ |
| 创意生成/头脑风暴 | ⭐⭐ | ⭐ | ⭐⭐⭐ |
| 多视角评审 | ⭐ | ⭐ | ⭐⭐⭐ |
| 代码开发全流程 | ⭐ | ⭐⭐⭐ | ⭐⭐⭐ |
| 知识综合报告 | ⭐⭐ | ⭐⭐ | ⭐⭐⭐ |
| 实时对话助手 | ⭐⭐⭐ | ⭐⭐ | ⭐ |
| 长文档处理 | ⭐ | ⭐⭐⭐ | ⭐⭐ |

### 4.3 工程化成本一览

| 工程维度 | 单 Agent | Sub-Agent | Agent Team |
|---------|---------|-----------|------------|
| **开发复杂度** | 低 | 中 | 高 |
| **运维难度** | 低 | 中 | 高 |
| **Prompt 工程量** | 低 | 中（N个 SubAgent 各一套） | 高（M个角色各一套） |
| **测试覆盖难度** | 低 | 中 | 高 |
| **可观测性需求** | 低 | 中（Trace 主控调度链路） | 高（全量消息追踪） |
| **成本可控性** | 高 | 高 | 低 |

## 五、深度场景分析：别光看表格，看实战

> 💡 **本章核心**：每种架构推荐都附带「为什么不用另一种」的论证——选型的关键往往在于排除法。

### 5.1 代码开发与 CI/CD 自动化 → Sub-Agent

以 Claude Code 为代表，典型流程：

```
Orchestrator（主控）
├── 需求分析 SubAgent → 生成技术方案文档
├── 代码生成 SubAgent → 编写代码
├── 代码审查 SubAgent → Review 代码质量
├── 测试生成 SubAgent → 生成单元测试
├── 执行 SubAgent    → 运行测试并反馈
└── PR 创建 SubAgent → 提交代码并创建 MR
```

**为何不用 Agent Team？** 代码开发有清晰的先后依赖（无法在代码写出来之前进行审查），流水线结构更自然。Agent Team 的对等通信在此场景会引入不必要的协商开销。

### 5.2 技术方案评审 → Agent Team

```
产品 Agent（分析需求合理性）
     ↕
架构师 Agent（评估技术可行性）
     ↕
安全 Agent（排查潜在风险）
     ↕
测试 Agent（评估可测试性）
     ↓
    综合裁判 Agent（汇总意见，生成评审结论）
```

**为何不用 Sub-Agent？** 评审需要多视角并行审阅和相互质询。各角色意见可能相互影响（安全问题可能改变架构决策），需要横向通信能力。

### 5.3 长文档处理 → Sub-Agent（Map-Reduce 模式）

```
Orchestrator
├── 分片 SubAgent × N（并行处理文档各段）
│   ├── Chunk 1 摘要 Agent
│   ├── Chunk 2 摘要 Agent
│   └── Chunk N 摘要 Agent
└── 归并 SubAgent（合并摘要，生成完整报告）
```

通过 Map-Reduce 模式突破单 Agent 上下文限制，每个 SubAgent 处理一小块，最后合并。

### 5.4 创意内容生成（如游戏世界观设计）→ Agent Team

```
世界观 Agent（宏观设定：时代背景、地理）
     ↕
角色 Agent（人物设定：背景故事、动机）
     ↕
剧情 Agent（故事线：主线、支线）
     ↕
美术方向 Agent（视觉风格参考）
     ↓
    整合 Agent（一致性检查与最终输出）
```

创意任务的特点是没有唯一正确答案，多样性和冲突往往能激发更好的创意。Agent Team 的「讨论」属性在此场景中是优势而非负担。

### 5.5 客户服务系统 → 混合架构

```
用户咨询
   │
   ▼
Router Agent（意图识别 + 分流）
   ├──→ 订单查询 SubAgent（工具调用型）
   ├──→ 投诉处理 Team（需要多角色评估）
   │      ├── 初审 Agent
   │      ├── 情感安抚 Agent
   │      └── 决策 Agent
   └──→ 技术支持 SubAgent（工具调用型）
```

现实系统往往需要两种架构的组合：简单意图走 Sub-Agent，复杂情况走 Agent Team。

## 六、Agent Team 实战手册

> 💡 **本章核心**：Agent Team 不是「多开几个 Agent」那么简单——角色怎么设计、上下文怎么传递、失控怎么兜底，才是真正的工程挑战。

### 6.1 角色设计三原则

**原则一：职责明确且互补，不要「复制粘贴型」角色**

```
❌ 错误示例：
  - Agent A：写代码
  - Agent B：也写代码（只是叫法不同）

✅ 正确示例：
  - 实现 Agent：根据需求编写代码
  - 批评 Agent：专门找代码问题（对抗性角色）
  - 优化 Agent：专注性能与可读性优化
```

**原则二：必须设计终止条件**

Agent Team 最常见的翻车是无限循环。三道防线：
- 轮次限制（最多 N 轮对话）
- 共识检测（Agent 输出趋于一致时自动终止）
- 质量门控（达到预设质量分数后停止迭代）

**原则三：设置仲裁机制**

当 Agent 之间产生分歧时：
- 指定权威 Agent（Supervisor 角色）做最终裁决
- 投票机制（多数决）
- 人工介入节点（Human-in-the-loop）

### 6.2 上下文怎么传：四种策略选哪个

| 策略 | 描述 | 适用场景 |
|------|------|----------|
| **全量广播** | 每个 Agent 看到所有历史消息 | 成员少（≤5），任务需要全局感知 |
| **摘要传递** | 每轮对话后生成摘要传给下一 Agent | 长任务，防止上下文膨胀 |
| **黑板共享** | 维护共享状态文档，Agent 按需读写 | 并行任务，状态需要持久化 |
| **定向传递** | 只传递与接收 Agent 相关的信息 | 流程固定，信息定向流转 |

### 6.3 反模式警示：那些踩过的坑

> ⚠️ 以下是 Agent Team 实践中最常见的失败模式，请对号入座。

**🚫 反模式一：「群体极化」—— AI 版 Groupthink**

如果没有对抗性设计，多个 Agent 会相互附和，产出表面「一致」但实际低质量的结果。

对策：
1. **引入魔鬼代言人（Devil's Advocate Agent）**：专门负责质疑所有输出
2. **盲评模式**：Agent 先独立生成结果，再进行对比
3. **多样性约束**：System Prompt 中要求提出不同观点
4. **置信度标注**：要求标注置信度，低置信度触发追问

**🚫 反模式二：「话痨团队」—— 通讯比干活多**

每次通信至少消耗 2 个 turn（一发一收），Agent 的 `max_turns` 有限。5 轮通信 = 10 个 turn 被吃掉。

对策：任务分发时**一次性给全信息**（需求 + 接口约定 + 规范），让每个 Agent 尽量自给自足。详见附录 A。

**🚫 反模式三：「人多手杂」—— Agent 数量 ≠ 效率**

潜在通讯线路 = `n(n-1)/2`，4 个 Agent 就有 6 条线路。经典的 Brooks 法则在 AI Agent 领域同样成立：

> *"Adding manpower to a late software project makes it later."*

对策：推荐 **2-4 个 Agent**，详见附录 A。

**🚫 反模式四：「回传淹没」—— Sub-Agent 也会撑爆主控（实战踩坑）**

> ⚠️ 这个反模式不仅限于 Agent Team，**Sub-Agent 架构同样存在**，而且更隐蔽。

Sub-Agent 设计的核心优势是「上下文隔离」——每个 SubAgent 有独立上下文，不会互相污染。但有一个容易忽略的盲区：**每个 SubAgent 完成后，交付物会回传给主控 Orchestrator，累积进主控的上下文中**。

```
实测场景（产品评审任务，3-5 个 SubAgent 并行）：

SubAgent A（PRD Review）     → 交付 280 行报告  → 回传主控
SubAgent B（技术评审）        → 交付 970 行报告  → 回传主控
SubAgent C（AI 团队综合评审）  → 交付 340 行报告  → 回传主控
SubAgent D（融合方案）        → 交付 310 行报告  → 回传主控

主控累计接收：~1900 行 ≈ 大量 Token → 上下文爆炸 → 任务卡死
```

**这与 Agent Team 的上下文膨胀本质相同**，只是路径不同：Team 是「横向通信累积」，Sub-Agent 是「纵向回传累积」。当 SubAgent 数量达到 3-5 个且每个都产出较长交付物时，主控同样会触及上下文上限。

对策：
1. **要求 SubAgent 返回摘要而非全文**：Prompt 中明确指定「交付不超过 N 行/N 字」，完整内容写入文件
2. **分阶段汇总**：不要等所有 SubAgent 完成后一次性汇总，而是每 2-3 个 SubAgent 完成后进行一次中间摘要压缩
3. **结果外置**：SubAgent 将详细结果写入文件系统，只向主控返回文件路径 + 关键结论摘要
4. **控制 SubAgent 数量**：单批并行的 SubAgent 建议不超过 3 个，更多的分批执行

> 💡 **核心教训**：Sub-Agent 的「上下文隔离」只隔离了输入侧，**输出侧的回传累积是隐形炸弹**。设计时必须同时控制输入和输出两端的上下文体积。

### 6.4 成本优化：让 Agent Team 不那么「烧钱」

| 优化手段 | 说明 | 节省效果 |
|---------|------|----------|
| **分层模型** | 简单 Agent 用小模型，核心 Agent 用强模型 | 成本降低 40-70% |
| **摘要压缩** | 每 N 轮对话后对历史进行摘要 | 上下文降低 60-80% |
| **并行调用** | 独立 Agent 同时执行 | 延迟降低 50% |
| **缓存重用** | 相同 System Prompt 开启 Prompt Caching | 成本降低 20-40% |
| **动态终止** | 质量评估器达标即停 | 避免无效轮次 |

### 6.5 可观测性：没有 Trace 就别上 Agent Team

```
必须有：
  ✅ 每条消息的来源 Agent 标识
  ✅ 每个 Agent 的完整输入/输出日志
  ✅ Token 消耗统计（按 Agent 分项）
  ✅ 执行时间 Trace

建议有：
  ⭐ Agent 之间的消息流向可视化（DAG 图）
  ⭐ 语义相似度检测（识别无效重复讨论）
  ⭐ 异常 Agent 行为告警（偏题、死循环）
  ⭐ A/B 测试框架（对比不同团队配置的效果）
```

## 七、混合架构：生产级系统的最终形态

> 💡 **本章核心**：纯粹的架构只存在于教科书中。真实世界里，80% 的路径用 Sub-Agent 走效率，20% 的决策用 Team 碰质量。

### 模式一：外 Team + 内 Sub-Agent

```
Agent Team（负责高层决策与协商）
  ├── 产品 Agent → 内部调用 SubAgent（需求分析工具）
  ├── 工程 Agent → 内部调用 SubAgent（代码生成+测试）
  └── QA Agent   → 内部调用 SubAgent（自动化测试执行）
```

适合：完整软件开发团队模拟

### 模式二：Sub-Agent + 内部微 Team

```
Orchestrator
  ├── 普通 SubAgent A（单 Agent 处理简单任务）
  ├── 普通 SubAgent B
  └── 复杂任务处理单元（内嵌小型 Agent Team）
         ├── 专家 Agent 1
         └── 专家 Agent 2
```

适合：大部分任务简单，少数任务需要深度协作

### 模式三：Router + 专门化子系统

```
入口 Router Agent（意图识别，任务路由）
  ├──→ 简单任务 → 单 Agent 处理
  ├──→ 结构化任务 → Sub-Agent 流水线
  └──→ 复杂决策任务 → Agent Team
```

适合：通用型 AI 助手系统

## 八、选型决策树

> 💡 **本章核心**：不确定选什么的时候，从这棵树的根节点开始走。

```
开始：你的任务是什么？
    │
    ├── 是否是单一简单问答或内容生成？
    │       ├── 是 → ✅ 单 Agent（带可选工具调用）
    │       └── 否 → 继续
    │
    ├── 任务是否有明确的先后依赖关系？
    │       ├── 是 → 考虑 Sub-Agent 架构
    │       │     ├── 是否需要多种专业工具？
    │       │     │       ├── 是 → ✅ Sub-Agent（工具分工型）
    │       │     │       └── 否 → ✅ 增强型单 Agent（ReAct）
    │       │     └── 是否需要大规模并行处理？
    │       │             ├── 是 → ✅ Sub-Agent（Map-Reduce 模式）
    │       │             └── 否 → ✅ Sub-Agent（流水线模式）
    │       └── 否 → 考虑 Agent Team 架构
    │
    ├── 任务是否需要多视角、多角色的深度协作？
    │       ├── 是 → ✅ Agent Team（角色专业化）
    │       └── 否 → 继续
    │
    ├── 质量要求是否极高（需要对抗性验证）？
    │       ├── 是 → ✅ Agent Team（加入 Critic Agent）
    │       └── 否 → 继续
    │
    ├── 是否同时有流水线任务和协作决策需求？
    │       └── 是 → ✅ 混合架构
    │
    └── 不确定？ → 从单 Agent 开始，按需演进
```

### Agent 间通信协议

除了框架层面的选型，Agent 之间的**通信标准化**也在快速演进：

| 协议 | 提出方 | 定位 | 说明 |
|------|--------|------|------|
| **MCP**（Model Context Protocol） | Anthropic | Agent ↔ 工具/数据源 | 标准化 Agent 调用外部工具和数据源的协议，类似 Agent 世界的 USB 接口 |
| **A2A**（Agent-to-Agent Protocol） | Google | Agent ↔ Agent | 标准化不同 Agent 之间的发现、认证和通信，解决跨框架互操作问题 |

> 📌 MCP 解决的是「Agent 如何连接工具」，A2A 解决的是「Agent 如何找到并对话另一个 Agent」。两者互补而非竞争。

## 十、总结与展望

### 核心结论（五句话记住全文）

1. **没有「最优」架构，只有「最适合」架构。** 架构选型应从任务特性出发，而非从框架特性出发。

2. **Sub-Agent 适合「确定性工程」**：任务边界清晰、流程可预见、需要工程化可靠性时，Sub-Agent 是首选。

3. **Agent Team 适合「创造性协作」**：任务开放、需要多视角、质量标准主观时，Agent Team 能发挥更大价值。

4. **混合架构是终点**：生产级系统几乎都是混合的——「外部 Team 做协商，内部 Sub-Agent 做执行」。

5. **从简单开始，按需演进**：除非有明确需求，否则从单 Agent 起步，遇到能力瓶颈时才引入复杂架构。

### 演进趋势

- **Agent 记忆体系的完善**：跨会话的长期记忆（Episodic Memory）将成为 Agent Team 维持一致性的关键
- **自适应团队组建**：根据任务动态决定需要几个 Agent、什么角色，而非静态配置
- **Agent 间信任机制**：Agent 之间可能引入信用评分，影响消息权重
- **标准化通信协议成熟**：MCP（Agent↔工具）和 A2A（Agent↔Agent）正在成为事实标准，未来可能出现统一的 Agent 互操作层
- **人类-Agent 混合团队**：Human-in-the-Loop 将在高风险决策场景中长期存在

## 附录 A：Agent Teams 通讯效率与团队规模实战指南

> 本附录基于 CodeBuddy IDE Agent Teams 实践经验，提供通讯效率优化和团队规模决策的**可操作建议**。与第六章互补：第六章讲「原则」，本附录讲「怎么落地」。

### A.1 通讯成本：每次消息传递到底消耗了什么？

```
Agent A 发消息给 Agent B
  │
  ├─ Agent B 被唤醒（消耗一个 turn）
  ├─ Agent B 读取消息 + 理解上下文
  ├─ Agent B 处理后回复
  ├─ Agent A 被唤醒（又消耗一个 turn）
  └─ Agent A 读取回复 + 继续工作
```

每次通讯至少消耗 **2 个 turn**（一发一收），而每个 Agent 有 `max_turns` 限制。如果 `max_turns=20`，通讯 5 轮就用掉 10 个 turn，只剩 10 个做正事。

还有两个隐性成本：**上下文膨胀**（每条消息进入接收方对话历史）和 **注意力稀释**（长上下文中的 Lost in the Middle 问题）。

### A.2 好的 vs 坏的通讯设计

**✅ 好的设计（总通讯 4 次）：**

```
主代理 → Agent A：你负责前端，需求是 XXX（1次）
主代理 → Agent B：你负责后端，API 规范是 YYY（1次）
Agent A → 独立工作
Agent B → 独立工作
Agent A → 主代理：前端完成了 ✅（1次）
Agent B → 主代理：后端完成了 ✅（1次）
```

**❌ 坏的设计（20+ 次）：**

```
Agent A → Agent B：你的 API 路径是什么？
Agent B → Agent A：/api/users
Agent A → Agent B：返回格式是什么？
... 循环 10 次 ...
```

> 💡 **核心原则：通讯是昂贵的，任务拆分时要让每个 Agent 尽量自给自足。**

### A.3 团队规模：推荐 2-4 个 Agent

| Agent 数量 | 适用场景 | 风险等级 |
|-----------|---------|:--------:|
| **1 个** | 不需要 Team，用 SubAgent 就行 | — |
| **2 个** | 前端+后端、研究+实现、编码+审查 | 🟢 最稳定 |
| **3 个** | 前端+后端+测试、设计+编码+文档 | 🟢 推荐上限 |
| **4 个** | 复杂项目的多模块并行 | 🟡 需要清晰的任务边界 |
| **5+ 个** | 极少数超大型任务 | 🔴 协调成本急剧上升 |

通讯线路数 = `n(n-1)/2`（2个→1条，3个→3条，4个→6条，5个→10条），二次方增长。

### A.4 Team 设计三问

在创建 Agent Team 之前，先回答三个问题：

1. **任务能拆成几个「独立」模块？** → 独立模块数 ≈ 理想 Agent 数
2. **模块之间需要多少「接口约定」？** → 接口越多，沟通成本越高。尽量把强耦合的工作放在同一个 Agent 里
3. **每个 Agent 的工作量够不够？** → 如果一个 Agent 只做 5 分钟的事，不值得单独开

### A.5 通讯黄金法则

| 法则 | 说明 |
|------|------|
| **最小化通讯** | 任务分发时一次性给全所有必要信息 |
| **最大化自治** | 每个 Agent 能独立完成任务，不需频繁请示 |
| **星型优于网状** | 所有协调走 Team Lead，避免 Agent 间直接频繁对话 |
| **接口先行** | 分发任务前先确定模块间的接口规范 |
| **批量汇报** | Agent 完成后一次性汇报，而非边做边汇报 |
